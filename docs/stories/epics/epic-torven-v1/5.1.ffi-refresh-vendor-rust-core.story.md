# Story 5.1 — ffi_refresh_vendor: expose vendor fetchers via on-demand FFI

**Story ID:** 5.1.ffi-refresh-vendor-rust-core
**Status:** Done
**Epic:** Torven v1.0 — Pivot macOS native (`epic-torven-v1`)
**Wave:** 5 — Settings + Real API
**Estimated Effort:** M (~1 dia — Rust-only; async FFI wiring + per-vendor dispatch + Keychain lookup + ffi_record_snapshot write-back)

---

## Story (User Story)

Como desenvolvedor do Torven, eu quero expor uma função FFI `ffi_refresh_vendor(vendor_name)` que executa o fetcher HTTP do vendor correspondente end-to-end — buscando a API key do Keychain, chamando a API real, e gravando o resultado em `usage_snapshots` via `ffi_record_snapshot` — para que a SwiftUI layer (Story 5.3) possa invocar um refresh real com uma única chamada FFI.

---

## Contexto e Motivação

Os fetchers de vendor (`crates/torven-core/src/vendors/{anthropic,openai,openrouter,zai}/fetch.rs`) foram migrados para `torven-core` em Wave 1 (Story 1.4) e existem como código Rust funcional desde então. Contudo, nenhuma função FFI expõe um "refresh agora" para o Swift layer — os snapshots no history.db vêm apenas de seeds de teste ou de code paths legados.

A milestone "testar com APIs reais" exige que o Swift layer possa solicitar `ffi_refresh_vendor("anthropic")` e receber de volta os dados reais, gravados no SQLite, prontos para o chart recarregar.

**Por que Story 5.1 antes de 5.2 (Settings UI)?**

Porque 5.1 é Rust-only e pode ser paralela à 5.2 após um breve alinhamento de interface. O @dev pode implementar 5.1 e 5.3 em paralelo ao @dev implementando 5.2 — as interfaces FFI definidas aqui (UDL) são o contrato que 5.3 consome. Na prática a ordem natural de execução por um único dev é 5.1 → 5.2 → 5.3, mas o design permite paralelismo com dois devs.

**Implicações de autenticação por vendor:**

| Vendor | Auth type | Fonte da credencial |
|---|---|---|
| anthropic | OAuth (`~/.claude/.credentials.json`) | `vendors/anthropic/creds.rs` (já lê o arquivo) |
| openai | OAuth (`~/.codex/auth.json` ou Keychain) | `vendors/openai/creds.rs` |
| openrouter | API key (Keychain blob) | `MacKeychainStore::get_accounts_blob("openrouter")` |
| zai | API key (Keychain blob) | `MacKeychainStore::get_accounts_blob("zai")` |

A função `ffi_refresh_vendor` deve delegar cada vendor para seu fetcher nativo — sem reimplementar autenticação. Se a credencial não for encontrada, retorna `RefreshFfiError::CredentialMissing`.

**Nota sobre Anthropic:** O fetcher Anthropic usa OAuth via `~/.claude/.credentials.json` — NÃO via Keychain blob. Isso é intencional (Story 1.20 migrou api_keys genéricas para Keychain, mas Anthropic usa OAuth mantido pelo Claude CLI). A Story 5.2 (Settings UI) mostrará um campo "Anthropic" mas ao invés de API key mostrará status do OAuth (conectado/desconectado) — ou deixará o campo vazio se o usuário não tiver Claude CLI instalado.

**Referências ADR:**
- ADR-2 (`docs/architecture/torven-v1-adr.md#adr-2`) — Keychain logic em Rust via `security-framework`; hot path: fetchers Rust buscam api_key diretamente do `MacKeychainStore`, sem roundtrip Swift
- ADR-4 — UniFFI UDL mode; `[Async]` annotation para funções com I/O de rede
- `CLAUDE.md` invariant: "API keys should no longer remain in config.toml. Use `ffi_keychain_get_blob` / `ffi_keychain_set_blob` helpers"

## Acceptance Criteria

**AC-1:** `crates/torven-core/src/torven_core.udl` estendido com:

```udl
enum RefreshFfiError {
    "CredentialMissing",   // Keychain blob ausente ou OAuth file não existe
    "NetworkError",        // HTTP request falhou (timeout, DNS, TLS)
    "ApiError",            // API respondeu com 4xx/5xx
    "ParseFailure",        // response shape inesperada
    "StorageError",        // ffi_record_snapshot falhou ao gravar no SQLite
};

// no namespace torven_core:
[Async, Throws=RefreshFfiError]
void ffi_refresh_vendor(string vendor_name);
```

**AC-2:** `crates/torven-core/src/uniffi_exports.rs` — implementação de `ffi_refresh_vendor`:
- `vendor_name` aceita os slugs canônicos `"anthropic"`, `"openai"`, `"openrouter"`, `"zai"` (case-sensitive, lowercase)
- Qualquer outro slug retorna `RefreshFfiError::CredentialMissing` com `tracing::warn!` (não panic)
- A função é `async` e marcada `[Async]` no UDL para não bloquear a thread principal Swift
- Fluxo por vendor:
  1. Busca credencial (Keychain blob ou OAuth file)
  2. Chama o `fetch_snapshot` do vendor com `reqwest::Client` recém-criado (sem estado compartilhado entre calls)
  3. Converte `FetchOutcome` → `UsageSnapshotInput` via helper interno
  4. Chama `ffi_record_snapshot(snapshot)` para gravar no history.db
  5. Retorna `Ok(())` — Swift não precisa do snapshot diretamente; ele recarrega o chart via `ffi_query_aggregated`

**AC-3:** `FetchOutcome → UsageSnapshotInput` conversion helper:
- Função interna (não exposta via FFI) `fn outcome_to_snapshot_input(vendor: &str, outcome: &FetchOutcome) -> UsageSnapshotInput`
- Campos mapeados:
  - `vendor`: o slug passado
  - `account_id`: `None` para anthropic/openai (single account); `Some(active_account_id)` para openrouter/zai (usando o ACTIVE_ACCOUNTS map já existente)
  - `ts`: `chrono::Utc::now().timestamp_millis()`
  - `cost_usd`, `tokens_used`, `pct_used`: extraídos do snapshot via `VendorSnapshot::*` enum
  - `metric_kind`: `"cost_usd_total"` para vendors que retornam custo; `"pct_used"` para vendors que retornam percentual

**AC-4:** Se o `HISTORY_DB` não estiver inicializado quando `ffi_refresh_vendor` for chamado, a função tenta inicializar com o caminho default (`~/Library/Application Support/Torven/history.db`) antes de prosseguir. Falha na inicialização → `RefreshFfiError::StorageError`.

**AC-5:** Erros mapeados com precisão:
- Keychain `errSecItemNotFound` → `RefreshFfiError::CredentialMissing`
- OAuth file não existe → `RefreshFfiError::CredentialMissing`
- `reqwest::Error` de rede → `RefreshFfiError::NetworkError`
- HTTP status 4xx/5xx → `RefreshFfiError::ApiError`
- `serde_json` parse failure → `RefreshFfiError::ParseFailure`
- `ffi_record_snapshot` `HistoryFfiError` → `RefreshFfiError::StorageError`

**AC-6:** `cargo test --workspace` continua passando (zero regressões). Nenhum teste de rede real obrigatório — testes de unidade cobrem o mapeamento de erros com mocks ou via `#[cfg(test)]`.

**AC-7:** `make build-core` (UniFFI bindgen + xcframework rebuild) produz Swift bindings com:
- `ffiRefreshVendor(vendorName: String) async throws` em `torven_core.swift`
- `RefreshFfiError` enum em `torven_core.swift`
- `xcodebuild` BUILD SUCCEEDED (sem erros de linkagem)

**AC-8 (opcional, recommended):** `tracing::info!` ao início e fim de cada vendor refresh com o vendor slug e duração total. Facilita debug de latência sem expor credenciais.

## Risks

| Risco | Severidade | Mitigação |
|---|---|---|
| `[Async]` FFI no UDL com runtime UniFFI: o runtime polling do UniFFI (UDL mode) pode ter restrições na forma como async functions internas usam Tokio. A Story 1.15 (AI Insights) já valida esse path com `async_compat::Compat` — reusar o mesmo padrão. | Medium | Reusar `async_compat::Compat` e o pattern da `request_insight_streaming` como modelo. Se não funcionar, usar `tokio::task::block_in_place` como fallback síncrono em thread dedicada. |
| Anthropic OAuth: `~/.claude/.credentials.json` pode não existir no ambiente de teste. | Low | AC-5 mapeia "file não existe" para `CredentialMissing` — app continua funcional para outros vendors. |
| reqwest `Client` recriado a cada call: ligeiramente menos eficiente que um shared client. | Low | Latência dominada pela rede (p50 ~300ms API Anthropic). Client creation é ~1ms. YAGNI para Wave 5 — otimizar em Wave 6 se aparecer em profiling. |
| `HISTORY_DB` lazy init (AC-4): conflito com init explícito que Swift já fez via `ffi_init_history`. | Low | `OnceLock::get_or_init` é idempotente — se já inicializado, a tentativa de AC-4 retorna a instância existente sem re-inicializar. Sem conflito. |
