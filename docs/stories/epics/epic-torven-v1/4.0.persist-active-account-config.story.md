# Story 4.0 — Persistir active-account map em config.toml via toml_edit

**Story ID:** 4.0.persist-active-account-config
**Status:** Ready
**Epic:** Torven v1.0 — Pivot macOS native (`epic-torven-v1`)
**Wave:** 4 — Main Window + Swift Charts
**Estimated Effort:** XS (~0.5 dia — Rust-only, sem Swift novo, fecha dispensation Wave 3)

---

## Story (User Story)

Como usuário do Torven que configurou accounts para múltiplos vendors e fez swaps no AccountPicker, eu quero que o meu último account ativo por vendor seja preservado entre restarts do app, para que não precise reselecionar manualmente toda vez que o app reiniciar.

---

## Contexto e Motivação

A Story 3.3 entregou o `set_active_account` FFI e a UI de AccountPicker funcional, mas deliberadamente deixou a persistência **in-memory only** — ao reiniciar o app, o active-account volta para o default. Isso foi aceito como dispensation de Wave 3 (documentado no Change Log da 3.3).

Esta story **fecha esse gap** antes de Wave 4 introduzir a Main Window e Swift Charts, onde o ViewModel precisará saber qual account está ativo para filtrar as queries de histórico corretamente.

**Decisão WAVE4-D2 (cravada):** Story 4.0 vem ANTES do Main Window — fecha gap Wave 3 dispensation antes de adicionar complexidade Wave 4. A infraestrutura de leitura já existe; o que falta é o path de escrita quando `set_active_account` muta o estado.

**Referências ADR:**
- `docs/architecture/torven-v1-adr.md` ADR-1 — workspace Cargo e invariante de atomic cache writes (tempfile + persist, per-vendor flock)
- `docs/architecture/torven-v1-adr.md` ADR-2 — Keychain logic em Rust; `Account.api_key = None` indica "leia do Keychain"; config.toml guarda metadata, não keys
- `CLAUDE.md` invariante: "Cache writes are atomic (tempfile + persist). Per-vendor `flock` guards concurrent writes"
- `CLAUDE.md` invariante: "API keys should no longer remain in config.toml. Use Keychain blob helpers"

**O que esta story NÃO entrega:**
- UI para editar budgets ou configurar accounts (Wave 5)
- Persistência de outros estados de UI (range selecionado, tab ativa, etc.)

## Acceptance Criteria

**AC-1:** `crates/torven-core/src/config.rs` contém nova função pública `save_active_accounts(active_map: &HashMap<String, String>) -> Result<(), ConfigError>`:
- Usa `toml_edit` para abrir o config.toml existente como documento editável
- Escreve ou atualiza tabela `[active_accounts]` com pares `vendor_id = "account_id"`
- Preserva todos os outros campos, comentários e formatação do arquivo (invariante toml_edit: não serializar do zero)
- Usa write atômico: escreve em arquivo temp e renomeia para o path final (padrão estabelecido no CLAUDE.md)

**AC-2:** `crates/torven-core/src/uniffi_exports.rs` — função `set_active_account(vendor_id: String, account_id: String)` chama `save_active_accounts` após mutação in-memory:
- Se `save_active_accounts` retorna `Ok(())`: estado in-memory e disco em sync, sem log especial
- Se `save_active_accounts` retorna `Err(_)`: estado in-memory já foi mutado (swap aconteceu), mas APENAS loga `warn!("set_active_account: falha ao persistir em disco: {err}")` — NÃO desfaz o swap in-memory, NÃO propaga erro para Swift (AC grante: falha de IO não quebra UX de swap)
- Sem mudança na assinatura FFI exposta ao Swift — Swift não precisa saber da persistência

**AC-3:** `crates/torven-core/src/config.rs` contém função `load_active_accounts() -> HashMap<String, String>`:
- Lê a tabela `[active_accounts]` do config.toml se existir
- Retorna `HashMap` vazio se a tabela não existir (sem erro — backward compat com configs antigos sem a seção)
- Chamada durante inicialização do `TorvenCoreBridge` para reconstituir o estado in-memory de active accounts

**AC-4:** Concorrência segura — a função `save_active_accounts` usa `flock` exclusivo no arquivo config.toml durante a janela de leitura/escrita, seguindo o padrão de atomic cache writes do projeto (ver CLAUDE.md invariante). Nenhum dado corrompido se o Settings overlay editar config.toml simultaneamente.

**AC-5:** toml_edit preserva comentários do usuário: dado um config.toml com:
```toml
# Minha config pessoal
[anthropic]
# chave primaria
accounts = []
```
Após `save_active_accounts`, o arquivo ainda contém os comentários acima; apenas a seção `[active_accounts]` foi adicionada/atualizada.

**AC-6:** Restart semântico preservado — após `set_active_account("openrouter", "acct-2")`, simular restart via `load_active_accounts()` retorna `{ "openrouter": "acct-2" }`.

**AC-7:** Teste Rust — `test_set_active_account_persists`: chama `set_active_account` com temp config.toml, lê o arquivo resultante diretamente, verifica que `[active_accounts]` contém o par correto.

**AC-8:** Teste Rust — `test_save_load_roundtrip_two_vendors`: salva active accounts para 2 vendors, faz load no temp config, verifica ambos preservados. Valida que campos pré-existentes no config não foram apagados.

## Tasks / Subtasks

- [ ] **T1 (AC-1, AC-3, AC-5) — Implementar `save_active_accounts` e `load_active_accounts` em `config.rs`**
  - Adicionar `toml_edit` como dependency em `crates/torven-core/Cargo.toml` se ainda não presente
  - Implementar `save_active_accounts(active_map: &HashMap<String, String>) -> Result<(), ConfigError>` com toml_edit document parse → upsert `[active_accounts]` → write atômico (tempfile + rename)
  - Implementar `load_active_accounts() -> HashMap<String, String>` com graceful empty return se seção ausente
  - Adicionar `flock` no config.toml durante escrita (padrão existente no projeto)

- [ ] **T2 (AC-2) — Modificar `set_active_account` em `uniffi_exports.rs`**
  - Após mutação in-memory existente, chamar `save_active_accounts(&current_active_map)`
  - Error handling: `match result { Ok(()) => {}, Err(e) => warn!("set_active_account: persist failed: {e}") }`
  - Assinatura FFI inalterada — `TorvenCoreBridge.swift` não precisa de nenhum ajuste

- [ ] **T3 (AC-3, AC-6) — Inicialização: carregar active accounts ao startup**
  - Identificar onde `TorvenCoreBridge` é inicializado em Rust (provavelmente `uniffi_exports.rs` ou módulo de init)
  - Chamar `load_active_accounts()` durante init e reconstituir HashMap de active accounts in-memory
  - Garantir que `get_active_account(vendor_id)` retorna o account correto após restart

  - Usar `fd-lock` crate (ou `fs2` — verificar qual o projeto já usa em cache writes) para `flock` exclusivo
  - Escopo do lock: apenas a janela de leitura do toml_edit doc + escrita do arquivo temp
  - Teste de concorrência não obrigatório em unit test (difícil de testar deterministicamente) — documentar o pattern no Change Log

- [ ] **T5 (AC-7, AC-8) — Testes Rust**
  - `test_set_active_account_persists`: temp dir + temp config.toml → `set_active_account` → ler arquivo → assert `[active_accounts]` correto
  - `test_save_load_roundtrip_two_vendors`: 2 vendors → save → load → assert ambos presentes e fields anteriores intactos
  - Rodar `cargo test -p torven-core` e verificar que novos testes passam sem regressão

## Risks

| Risco | Severidade | Mitigação |
|---|---|---|
| Concorrência com Settings overlay: ambos editam config.toml ao mesmo tempo | Medium | flock exclusivo (AC-4); Settings overlay já tem pattern similar para api_key fields |
| `toml_edit` corrompe formato ao atualizar seção existente (whitespace, order) | Low | AC-5 exige teste de preservação de comentários; toml_edit é designed para edição não-destrutiva |
| config.toml sem seção `[active_accounts]` em instâncias antigas (upgrades) | Low | AC-3 garante `load_active_accounts` retorna HashMap vazio se seção ausente — graceful backward compat |
| Falha de IO em disco cheio ou permissão: swap in-memory ok, mas config não persistido | Low | AC-2 define comportamento exato: log warn, não reverter swap. Documentar no Change Log |
| `toml_edit` não estava nas deps: adicionar pode quebrar compilação de outros módulos | Low | Verificar Cargo.toml antes de adicionar; se já presente (Story 1.6 provável), zero overhead |
