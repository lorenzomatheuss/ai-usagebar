# Story 3.1 — VendorCard.swift skeleton (parametrizado por VendorInfo, OpenRouter first)

**Story ID:** 3.1.vendor-card-skeleton
**Status:** Done
**Epic:** Torven v1.0 — Pivot macOS native (`epic-torven-v1`)
**Wave:** 3 — Vendor Cards + Account Picker
**Estimated Effort:** M (~1 dia — 1 arquivo Swift novo + smoke integration em PopoverView, placeholders estáticos sem nova FFI)

---

## Story (User Story)

Como desenvolvedor do Torven preparando os 5 vendor cards na Wave 3, eu quero criar `apple/Torven/Popover/VendorCard.swift` como uma view parametrizada (`init(vendor: VendorInfo)`) com a estrutura visual completa do card — cabeçalho com displayName + indicador `isConfigured`, linha de cost ("$ -- this period"), linha de budget ("--% used"), e um sparkline placeholder (Rectangle ou SF Symbol `chart.xyaxis.line`) — para que a Story 3.2 só precise embrulhar essa view num `ForEach(coreBridge.vendors)` sem ter que decidir layout de card, e para que o vendor OpenRouter já apareça **uma vez** no popover provando que a estrutura compila, marshala VendorInfo e respeita o frame 360×420 do PopoverView herdado da Wave 2.

---

## Contexto e Motivação

A Wave 2 (Stories 2.1/2.2/2.3) deixou `PopoverView` com header "Torven" + área vazia 360×420. A Wave 3 preenche essa área com os 5 vendor cards. Esta story é o primeiro passo: criar a unidade de UI reutilizável (`VendorCard`) com **placeholders estáticos** para os dados que ainda não cruzaram FFI nesta wave (cost/budget%/sparkline real chegam em Wave 4 com Swift Charts + history queries).

**Por que OpenRouter primeiro:** Decisão Lorenzo no kickoff Wave 3 (2026-06-04, handoff `wave3-kickoff-master-to-sm`): ADR §11 entry 11 cita explicitamente "Vendor card — first vendor (OpenRouter)". OpenRouter é multi-modelo e tem displayName mais longo que "OpenAI" ou "Z.AI", validando o shape do card sob string com risco real de truncar.

**Por que placeholders estáticos para métricas:**
- `VendorInfo` (em `torven_core.udl`) atualmente expõe apenas `id`, `display_name`, `is_configured`.
- Dados de cost/budget/tokens reais existem em `HistorySnapshot` (cost_usd, tokens_used, pct_used), mas conectar history queries ao card é escopo Wave 4 (ADR §11 entry 16 — Main window + Swift Charts).
- Tentar plugar cost real nesta story incharia escopo (precisa de Story 1.13 wiring + agregação por janela temporal). Skeleton entrega valor: shape visual pronto, parametrizado, reutilizável.

**O que esta story entrega:**
- `apple/Torven/Popover/VendorCard.swift` — struct `VendorCard: View` com `let vendor: VendorInfo` no init e placeholders estáticos para métricas
- `PopoverView.swift` modificado para procurar OpenRouter em `coreBridge.vendors` e renderizar `VendorCard(vendor:)` **uma vez** abaixo do header (proof of integration)
- Header "Torven" preservado; restante do espaço continua vazio até Story 3.2 fazer o ForEach

**Referências:**
- `docs/architecture/torven-v1-adr.md#4` — tabela "NEW (Apple side)" lista `Popover/VendorCard.swift` como "Per-vendor card (config + 1 account)"
- `docs/architecture/torven-v1-adr.md` §11 Story Roadmap entry 11 — "Vendor card — first vendor (OpenRouter)"
- `crates/torven-core/src/torven_core.udl` linhas 68-72 — dictionary `VendorInfo`

- **Header row:** `vendor.displayName` (font `.headline`) + indicador `isConfigured` (`Image(systemName:)` — `checkmark.circle.fill` verde quando true, `circle` cinza quando false). Mesmo padrão que `VendorListView_Story15.swift` para coerência visual.
- **Metrics row:** texto estático placeholder na forma `"$— this period"` (cost) e `"—% used"` (budget). String literal exatamente com travessão tipográfico (`—`, U+2014) para sinalizar visualmente "dado ainda não disponível" sem parecer bug.
- **Sparkline placeholder:** `Rectangle` cinza claro (`Color.secondary.opacity(0.15)`) com altura fixa 24pt OU `Image(systemName: "chart.xyaxis.line").foregroundColor(.secondary)` — qualquer um dos dois aceito; ponto é ocupar visualmente o espaço onde a chart real entra em Wave 4.

**AC-3:** Body mínimo aceito (variações de spacing/alignment OK contanto que as 3 regiões existam e o placeholder visual seja distinguível):
```swift
var body: some View {
    VStack(alignment: .leading, spacing: 6) {
        HStack {
            Text(vendor.displayName)
                .font(.headline)
            Spacer()
            Image(systemName: vendor.isConfigured ? "checkmark.circle.fill" : "circle")
                .foregroundColor(vendor.isConfigured ? .green : .secondary)
        }
        HStack {
            Text("$— this period")
                .font(.subheadline)
                .foregroundColor(.secondary)
            Spacer()
            Text("—% used")
                .font(.subheadline)
                .foregroundColor(.secondary)
        }
        Rectangle()
            .fill(Color.secondary.opacity(0.15))
            .frame(height: 24)
    }
    .padding(12)
    .background(
        RoundedRectangle(cornerRadius: 8)
            .fill(Color.gray.opacity(0.08))
    )
}
```
A versão acima é referência canônica; @dev pode ajustar paddings, cornerRadius (4-12pt), e opacity contanto que o card seja visualmente um cartão (não uma linha de tabela).

## Dev Notes

### Por que skeleton (e não card "real" com cost de history)

`VendorInfo` no `torven_core.udl` atual expõe apenas:
```
dictionary VendorInfo {
    string id;
    string display_name;
    boolean is_configured;
};
```
Cost/budget/tokens vivem em `HistorySnapshot` (campos `cost_usd`, `tokens_used`, `pct_used`) e exigem uma query agregada via `ffi_query_snapshots` por janela temporal — esse wiring (aggregation + cache) é escopo Wave 4 (ADR §11 entry 16 — Main window + Swift Charts). Forçar real cost nesta story explode escopo e bloqueia 3.2.

**Solução de escopo:** placeholder visual estático com travessão tipográfico (`—`) sinaliza "dado pendente" sem parecer bug. Quando Wave 4 entregar agregação real, troca `Text("$— this period")` por `Text("$\(cost, specifier: "%.2f") this period")` — diff de 1 linha por métrica.

### Por que VendorCard recebe `let vendor: VendorInfo` em vez de ler do bridge

Constructor injection escala melhor que `@EnvironmentObject` quando o componente vai ser usado em múltiplos contextos:
- Story 3.2 (ForEach): cada iteração injeta o `VendorInfo` da iteração
- Wave 4 (history view): potencial reutilização em janela detalhada de histórico onde o vendor vem de query, não de coreBridge
- Tests/previews: pode ser construído com mock sem precisar instanciar `TorvenCoreBridge`

`PopoverView` ainda usa `@EnvironmentObject` para escolher qual `VendorInfo` passar — esse é o lugar certo do bridge.

### OpenRouter primeiro: AUTO-DECISION confirmada por kickoff

Decisão cravada por Lorenzo no kickoff Wave 3 (2026-06-04, handoff `wave3-kickoff-master-to-sm`, ponto §"elicitação Lorenzo"):

> "First vendor em 3.1: **OpenRouter** (ADR §11 entry 11; multi-modelo valida shape com mais sinal visual)"

OpenRouter:
- Tem displayName de 10 caracteres ("OpenRouter") — mais longo que "OpenAI" (6) ou "Z.AI" (4) — testa truncate behavior antecipadamente
- É multi-modelo (gpt-4, claude-3, llama, etc.) — em waves futuras valida que o card aguenta mostrar "model picker" sob o cabeçalho
- ADR §11 entry 11 cita explicitamente OpenRouter como first vendor

### Frame 360×420 NÃO muda nesta story

UX-Q1 (sizing trade-off 360×420 vs 380×540) está **aberta** e é fechada definitivamente em Story 3.2 — quando o ForEach renderiza os 5 cards e dá pra medir empiricamente se cabem sem scroll no 360×420 ou se precisa subir para 380×540.

Story 3.1 renderiza apenas 1 card → 360×420 trivialmente comporta. Não há pressão dimensional aqui.
