## Story (User Story)

Como usuário do Torven que pressiona ⌘, para configurar minhas API keys, eu quero que a janela Settings abra corretamente — sem disparar `NSViewBridgeErrorCanceled` no Console e sem encerrar o app ao fechar — para que eu possa salvar minhas credenciais e usar o botão Refresh com minhas contas reais.

---

## Decisão FINAL — WAVE5-D8-impl-v4 (Pragmática 2)

Após 3 iterações falhas em torno da SwiftUI `Settings { }` scene, foi cravada a saída definitiva: **bypassa a scene inteiramente**. Settings UI agora vive em um `NSWindowController` custom (mesmo pattern da `MainWindowController` da Story 4.1, já em produção desde Wave 4 com smoke 37/40 PASS).

**Componentes-chave:**
- `apple/Torven/Settings/SettingsWindowController.swift` (NEW, ~115 LOC) — singleton `NSWindowController + NSWindowDelegate`. Wrap o SwiftUI `SettingsView()` via `NSHostingView`. `windowShouldClose` retorna `false` + `orderOut(nil)` — mesma técnica do MainWindowController para preservar state entre aberturas.
- `apple/project.yml` — `LSUIElement: true` **preservado** (re-habilitado após iter 3). App segue menu-bar-only sem dock icon.
- `apple/Torven/TorvenApp.swift` — Settings SwiftUI scene **REMOVIDA**. `⌘,` agora wired via `KeyboardShortcuts.Name.openSettings` (default `.comma`/`.command`), mesmo pattern de `⌘1` da Story 4.1.
- `apple/Torven/AppDelegate.swift` — minimal defensive (`applicationShouldTerminateAfterLastWindowClosed { false }`). Não load-bearing nesta iter — `LSUIElement: true` já garante o lifecycle correto — mas mantido como defesa-em-profundidade e ponto de extensão pra Story 1.15 (Keychain-shutdown wiring).

**Por que vai funcionar (não-falsificável):**
- `MainWindowController` provou o padrão em produção (Story 4.1 Wave 4, smoke 37/40 PASS, Wave 4 polish #2 mergeada). Mesmo pattern, zero ViewBridge XPC.
- `NSWindow` programático não passa por XPC handshake → ativação policy `.accessory` (LSUIElement) não cancela.
- `LSUIElement: true` no Info.plist preserva o status menu-bar-only no nível do macOS, não dependendo de `applicationShouldTerminateAfterLastWindowClosed` em runtime.

## Histórico das 3 iterações abandonadas

### Iter 1 (commit `8c620ee`, resetado) — Opção A2

`.onAppear`/`.onDisappear` em SettingsView faziam flip de `NSApp.activationPolicy` entre `.accessory` e `.regular`. **Smoke FAIL:** app encerrou ao fechar Settings (sem AppDelegate, NSApp default termina quando última `.regular` window fecha).

### Iter 2 (commit `1992ed1`, resetado) — Opção A1

AppDelegate completo (~190 LOC) com `applicationShouldTerminateAfterLastWindowClosed { false }` + observers `didBecomeKeyNotification`/`willCloseNotification` filtrados por `window.title == "Torven Settings"`. **Smoke FAIL:** `NSViewBridgeErrorCanceled` persistente — `didBecomeKey` é post-event, então o ViewBridge cancel já tinha ocorrido antes do flip `.accessory → .regular`. Race condition fundamental do macOS.

### Iter 3 (commit `dbbd0f1`, resetado) — Pragmática 1

Dropar `LSUIElement: true`. App rodando `.regular` desde launch + AppDelegate keep-alive. **Smoke FAIL:** AC-1/2/4/6 PASS mas AC-3 FAIL — app ainda encerrava ao fechar Settings mesmo com `applicationShouldTerminateAfterLastWindowClosed { false }` retornando falso. Causa: quirk `MenuBarExtra` + `Settings { }` scene lifecycle em macOS 13+ que AppDelegate adapter não segura.

### Iter 4 (esta — Pragmática 2 FINAL)

Bypassa a `Settings { }` SwiftUI scene inteiramente. NSWindowController custom + NSHostingView wrapping SettingsView. LSUIElement preservado. KeyboardShortcuts wires ⌘,. **Build gate verde.** Smoke runtime pendente Lorenzo.
