# Story 1.6 — Config migration para Vec<Account> shape (FR-6 multi-account schema)

**Story ID:** 1.6.config-migration
**Status:** Done
**Epic:** Torven v1.0 — Pivot macOS native
**Estimated Effort:** M (1 dia)

---

## Story (User Story)

Como desenvolvedor do Torven, eu quero refatorar `Config` em `torven-core` para suportar `accounts: HashMap<VendorId, Vec<Account>>` com campos `name`, `api_key`, `description`, `budget_usd` e `tag`, incluindo migration automática do formato antigo (single `api_key` por vendor) para o novo, para que o sistema suporte multi-account desde o início (FR-6) e o `config.toml` de usuários existentes seja migrado com aviso em vez de quebrar.

---

## Contexto e Motivação

O schema atual de `Config` tem uma única `api_key` por vendor (ex: `[openrouter] api_key = "sk-or-..."`). O PRD FR-6 exige múltiplas accounts por vendor para OpenRouter e Z.AI — cada uma com `name`, `tag`, `budget_usd`, `description` opcional.

Esta story refatora o `Config` struct e o schema TOML **antes** de qualquer código de Keychain ou UI de accounts (Stories 1.20 e Story 14 do Grupo 2), garantindo que o modelo de dados esteja correto desde cedo.

**Importante:** As api_keys permanecem no TOML nesta story — a migração para Keychain é Story 1.20. Por ora, api_key no Account struct é `Option<String>` — ausente significa "usar Keychain" (depois que a Story 1.20 completar).

**Pode rodar em paralelo com Story 1.5** após Story 1.4 completar.

**Referência:** `docs/prd/torven-v1.md#fr-6` (FR-6 Multi-Account) e `docs/architecture/torven-v1-adr.md#4-cleanup-plan` (config.rs MIGRATE).

## Acceptance Criteria

**AC-1:** `Account` struct definida em `crates/torven-core/src/config.rs`:
```rust
pub struct Account {
    pub name: String,
    pub api_key: Option<String>,  // None = "usar Keychain" (Story 1.20)
    pub description: Option<String>,
    pub budget_usd: Option<f64>,
    pub tag: Option<AccountTag>,
}

pub enum AccountTag { Client, Personal, Team }
```

**AC-2:** `Config` struct atualizado com:
```rust
pub struct Config {
    pub accounts: HashMap<VendorId, Vec<Account>>,
    pub ai_insights: AiInsightsConfig,
    pub history: HistoryConfig,
    pub display: DisplayConfig,  // thresholds, refresh_interval, etc.
}
```

**AC-3:** TOML parser suporta formato novo:
```toml
[[openrouter.accounts]]
name = "ClienteAcme"
api_key = "sk-or-..."
tag = "client"
budget_usd = 200.0

[[openrouter.accounts]]
name = "Personal"
api_key = "sk-or-xxx"
tag = "personal"
```

**AC-4:** TOML parser faz migration automática do formato antigo:
```toml
# Formato antigo (antes do pivot)
[openrouter]
api_key = "sk-or-..."
```
→ converte automaticamente para `Account { name: "default", api_key: Some("sk-or-..."), ... }` com log de aviso: `"[WARN] Config migrated from legacy single-key format. Please review accounts section."`

**AC-5:** Testes unitários cobrem:
- Parse de config TOML novo com múltiplas accounts por vendor
- Migration de config legado para novo formato
- Serialização de volta para TOML (usando `toml_edit` para preservar comentários)
- Validação: `budget_usd >= 0`, `name` não vazio, `api_key` só alphanumeric/hifens/underscores

**AC-6:** `config.example.toml` no root atualizado com o novo schema, comentado, com exemplos de multi-account para OpenRouter e Z.AI.

**AC-7:** `cargo test -p torven-core` com ao menos 10 testes unitários de config passa.

## Dev Notes

### Architecture References

- **FR-6** (`docs/prd/torven-v1.md#fr-6`): especificação detalhada do multi-account. Cada account tem `name` (único por vendor), `api_key` (para Keychain em v1.0), `description?`, `budget_usd?`, `tag?`.
- **ADR-2** (`docs/architecture/torven-v1-adr.md#adr-2`): Keychain híbrido — o blob JSON do Keychain será `[{account_id, api_key}]` por vendor. O `Account.api_key` no TOML é apenas para migration e backwards compat durante desenvolvimento.
- **ADR-1 cleanup plan** (`docs/architecture/torven-v1-adr.md#4-cleanup-plan`): `config.rs` MIGRATE — adicionar `accounts`, `ai_insights`, `history`. Manter TOML parsing + `toml_edit`.
- **R-6** (`docs/prd/torven-v1.md#9-risks`): risco de Keychain prompts repetitivos. Mitigação: single Keychain item por vendor com JSON blob de todas accounts.

### Nota sobre api_key em Account

Por ora (Stories 1.1-1.19), `api_key` fica no `Account` struct como `Option<String>`. Quando Story 1.20 (Keychain) completar, o fluxo muda:

1. Settings UI permite ao usuário "mover key para Keychain" — move api_key do TOML para o blob Keychain e seta `account.api_key = None` no TOML
2. Fetchers verificam: se `account.api_key.is_some()`, usar; se `None`, chamar `keychain_get_blob(vendor)`

Isso garante backward compat para devs que rodam sem Keychain (ex: CI smoke tests).

### Account ID

O `account_id` usado em SQLite e em hashes de privacidade (FR-7 AI Insights) é derivado de `format!("{}-{}", vendor_id, account_name).to_lowercase()` — determinístico, sem UUID aleatório. Isso permite que a migration de config legado gere IDs estáveis.
