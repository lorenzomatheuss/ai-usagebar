# Story 4.6 — Budget burn indicator (gauge progress) + budgets em config.toml

**Story ID:** 4.6.budget-burn-indicator
**Status:** Ready
**Epic:** Torven v1.0 — Pivot macOS native (`epic-torven-v1`)
**Wave:** 4 — Main Window + Swift Charts
**Estimated Effort:** M (~1 dia — Rust budgets.rs + UDL extension + get_budget_status FFI + SwiftUI BudgetBurn gauge)

---

## Story (User Story)

Como usuário do Torven que definiu limites de gasto mensais para minha conta, eu quero ver um indicador visual de "queima de orçamento" — mostrando quanto do budget mensal já consumi — para que eu saiba antes de exceder o limite e possa ajustar meu uso proativamente.

---

## Contexto e Motivação

As Stories 4.3-4.5 entregam análise histórica de custo. Esta story fecha a Wave 4 com a feature de **orçamento**: um gauge (barra de progresso radial ou linear) que compara o gasto do mês atual com um limite configurado pelo usuário.

**Decisão WAVE4-D6 (cravada):** Budgets hard-coded em `config.toml [budgets]` seção — editável manualmente em Wave 4. Wave 5 transforma em UI editável no Settings panel. Isso mantém Wave 4 focado e não polui o escopo com Settings UI antecipada.

**Decisão WAVE4-D2 (contexto):** Story 4.0 fecha a persistência de active accounts. Esta story segue o mesmo padrão: Rust core lê config, expõe via FFI, Swift UI consome. Nenhuma nova persistência é adicionada — somente leitura do config.toml.

**Arquitetura:**
```
config.toml [budgets] ──► budgets.rs (parse) ──► get_budget_status FFI ──► BudgetBurn.swift (gauge)
                                                       ↑
                                         HistoryDb::query_aggregated (mês corrente, reusa lógica Story 4.0.5)
                                         OU SQL inline em budgets.rs se mais simples
```

`get_budget_status` é uma FFI de leitura no server-side; Swift NÃO chama `ffi_query_aggregated` separadamente para o gauge — toda a agregação do mês acontece em Rust dentro de `get_budget_status`.

**Integração com Wave 4:**
O `BudgetBurn` pode viver no sidebar da Main Window, abaixo dos charts, ou como barra no topo — a localização exata é decisão do @dev com olho em layout. A story define que deve estar visible na Main Window; onde exatamente é flexibilidade de implementação.

**Referências ADR:**
- `docs/architecture/torven-v1-adr.md` ADR-5 — SQLite + history layer (gasto do mês corrente calculado server-side em Rust, reusando `HistoryDb::query_aggregated` da Story 4.0.5)
- `docs/architecture/torven-v1-adr.md` ADR-2 — config.toml como store de metadata (api_key = Keychain; budgets = config.toml é adequado pois não são dados sensíveis)
- `CLAUDE.md` invariante: "API keys should no longer remain in config.toml" — budgets NÃO são api_keys, é config de UI; safe em config.toml

## Acceptance Criteria

**AC-1:** `config.toml` aceita nova seção `[budgets]`:
```toml
[budgets]
monthly_usd_total = 100.0

[budgets.per_vendor]
openrouter = 50.0
anthropic = 30.0
openai = 20.0
```
- Seção é **opcional**: se ausente, `BudgetBurn` não renderiza (AC-5). Não quebrará configs existentes.
- `monthly_usd_total` é o limite global; `per_vendor` é opcional dentro de `[budgets]`

**AC-2:** `crates/torven-core/src/budgets.rs` criado com:
- Struct `BudgetConfig` com `monthly_usd_total: Option<f64>` e `per_vendor: HashMap<String, f64>`
- Função `parse_budgets(config_path: &Path) -> Result<BudgetConfig, ConfigError>` que lê a seção `[budgets]` via `toml_edit` ou `toml` crate (confirmar qual o projeto usa)
- Edge cases tratados: valor negativo → retorna erro; valor zero → aceito (budget de $0 = any spend triggers red); seção ausente → retorna `BudgetConfig { monthly_usd_total: None, per_vendor: HashMap::new() }`

**AC-3:** `crates/torven-core/src/torven_core.udl` estendido com:
```
dictionary VendorBudgetStatus {
    string vendor_id;
    double spent_usd;
    double budget_usd;
    double percent_used;  // spent / budget * 100
};

dictionary BudgetStatus {
    double total_spent_usd;
    double? total_budget_usd;   // null se não configurado
    double total_percent_used;
    sequence<VendorBudgetStatus> per_vendor;
    boolean has_budget;         // false se seção [budgets] ausente
};

// no namespace torven_core:
BudgetStatus get_budget_status();
```

**AC-4:** `crates/torven-core/src/uniffi_exports.rs` — implementação de `get_budget_status()`:
- Carrega `BudgetConfig` via `parse_budgets`
- Calcula `total_spent_usd` em Rust para o mês corrente em UTC (início do mês = 00:00:00 UTC do dia 1) reusando `HistoryDb::query_aggregated(...)` da Story 4.0.5 com `BucketStrategy::Daily` (ou maior) e SUMmando os buckets, OU query SQL inline se mais simples (sem dependência de buckets temporais — apenas SUM por vendor)
- Popula `per_vendor` com status de cada vendor que tem budget definido
- Se `has_budget == false`, retorna imediatamente sem query a SQLite (otimização: sem DB I/O desnecessário)

**AC-5:** `apple/Torven/MainWindow/BudgetBurn.swift` criado com:
- View `BudgetBurn: View` recebendo `status: BudgetStatus`
- Se `status.hasBudget == false`: retorna `EmptyView()` — sem render, sem crash
- Se `hasBudget == true`: exibe `Gauge(value: status.totalPercentUsed, in: 0...100) { Text("Budget") }` com label `"$\(status.totalSpentUsd, specifier: "%.2f") / $\(status.totalBudgetUsd ?? 0, specifier: "%.2f")"` abaixo
- Cor do gauge: verde < 80%, amarelo 80-99%, vermelho >= 100% (via `.tint(burnColor)`)
- `burnColor: Color` computed property baseada em `totalPercentUsed`

**AC-6:** `MainWindowView.swift` inclui `BudgetBurn` no layout:
- Localização recomendada: rodapé da content area (abaixo dos charts) ou sidebar (se layout de sidebar existir)
- Decisão final de layout é do @dev — documentar no Change Log onde foi colocado
- `BudgetBurn` recebe `status` do `ChartViewModel` ou de `@EnvironmentObject TorvenCoreBridge`

**AC-7:** Reset mensal correto: `total_spent_usd` considera apenas snapshots com `ts` no mês calendario atual em UTC. Exemplo: em junho/2026, inclui snapshots de 2026-06-01T00:00:00Z a 2026-06-30T23:59:59Z.

**AC-8:** Testes Rust:
- `test_parse_budgets_full`: config.toml com `[budgets]` completo → `BudgetConfig` correto
- `test_parse_budgets_absent`: config.toml sem `[budgets]` → `BudgetConfig { monthly_usd_total: None, ... }`
- `test_parse_budgets_negative`: valor negativo → `Err(ConfigError::...)` 
- `test_budget_status_monthly_reset`: mês corrente calculado corretamente (mock de `chrono::Utc::now()` ou passar timestamp como parâmetro para testabilidade)

**AC-9:** `accessibilityReduceMotion` respeitado: transições de cor do gauge (verde/amarelo/vermelho) sem animação custom se `reduceMotion` ativo.

**AC-10 (opcional):** `#Preview` em `BudgetBurn.swift` com 3 estados: verde (50% used), amarelo (85% used), vermelho (115% used).

## Risks

| Risco | Severidade | Mitigação |
|---|---|---|
| Timezone edge case: `total_spent_usd` usa UTC mas usuário está em GMT-3 — gasto de 31/mai às 23h local conta em junho UTC | Medium | AC-7 define UTC explicitamente; documentar no Change Log como limitação conhecida; Wave 5 pode adicionar timezone preference. Usuário pode observar discrepância de até 24h no reset. |
| `Gauge` view em macOS 13 vs 14+ com styles diferentes: `.accessoryLinear` pode não existir em 13 | Medium | Verificar disponibilidade de `gaugeStyle` in macOS 13; usar `ProgressView` como fallback se `Gauge` não disponível. `Gauge` foi introduzido no watchOS e chegou no macOS 13 via SwiftUI — confirmar experimentalmente. |
| `get_budget_status()` é síncrono FFI: se a agregação do mês (via `HistoryDb::query_aggregated` ou SQL inline) for lenta com muitos snapshots, pode travar | Low | Chamar dentro de `Task { }` em Swift, assim como as outras FFI calls de chart. Se a função for marcada `[Async]` no UDL: ainda melhor. |
| UDL regeneration: adicionar novos dictionaries pode quebrar Swift build se algum campo tem tipo não mapeado (ex: `Option<f64>` vira `Double?` no Swift — ok; mas `HashMap` precisa ser `sequence` no UDL) | Medium | Verificar mapeamento de tipos antes de commitar UDL; `per_vendor: HashMap<String, f64>` deve virar `sequence<VendorBudgetStatus>` (com struct wrapper) — não usar HashMap diretamente no UDL |
| Layout da Main Window com 3 elementos (DateRangePicker + charts + BudgetBurn): pode ficar muito denso | Low | Localização do BudgetBurn é flexível (AC-6). Rodapé com tamanho fixo ~60pt é uma boa opção — não compete com os charts. |

## Out of Scope

- UI para editar os budgets (Wave 5 Settings panel — Decisão WAVE4-D6 cravada)
- Alertas/notificações quando budget é excedido (Wave 5)
- Budget por account (somente por vendor na Wave 4)
- Budget em outras moedas além de USD
- Budget semanal ou por range customizado (apenas mensal)
- Sincronização de budgets entre máquinas (v1.5 cloud sync)
