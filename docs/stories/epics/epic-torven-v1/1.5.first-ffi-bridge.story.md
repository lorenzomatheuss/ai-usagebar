# Story 1.5 — First FFI bridge: get_vendor_list() + consumir em Swift skeleton

**Story ID:** 1.5.first-ffi-bridge
**Status:** Done
**Epic:** Torven v1.0 — Pivot macOS native
**Estimated Effort:** M (1 dia, incluindo spike AR-3 memory profiling 0.5d)

---

## Story (User Story)

Como desenvolvedor do Torven, eu quero expor `get_vendor_list() -> Vec<VendorInfo>` via UniFFI UDL e consumir o resultado em `TorvenCoreBridge.swift` no app SwiftUI, para que eu possa confirmar o fluxo completo Rust → FFI → Swift → UI funcionando com dados reais de negócio (lista de 5 vendors).

---

## Contexto e Motivação

As stories 1.1, 1.2 e 1.4 estabeleceram o workspace e o pipeline UniFFI com uma função `ping()` trivial. Esta story eleva o nível: expõe uma função real de negócio (lista de vendors) via FFI, valida o type marshalling de structs customizadas (`VendorInfo`) e estabelece o `TorvenCoreBridge.swift` como padrão de consumo do Rust core no Swift.

Esta story também executa o **spike de memory profiling AR-3** — usar `leaks` do macOS para confirmar que a passagem de `Vec<VendorInfo>` pelo FFI não vaza memória.

**Ao final desta story:** Swift roda, chama `getVendorList()`, recebe array de 5 vendors (`["anthropic", "openai", "openrouter", "zai", "gemini"]`), e os exibe em um `List` SwiftUI no popover.

**Referência:** `docs/architecture/torven-v1-adr.md#adr-4` (FFI surface do UDL) e `docs/architecture/torven-v1-adr.md#adr-10` (TorvenApp.swift + TorvenCoreBridge).

## Acceptance Criteria

**AC-1:** `VendorInfo` struct declarada no UDL:
```udl
dictionary VendorInfo {
    string id;
    string display_name;
    boolean is_configured;
};
```

**AC-2:** Função `get_vendor_list() -> sequence<VendorInfo>` declarada no UDL e implementada em Rust com os 5 vendors hardcoded (por enquanto — config real vem na Story 1.6).

**AC-3:** `apple/scripts/build-xcframework.sh` implementado para gerar `TorvenCore.xcframework` single-arch quando só `aarch64-apple-darwin` estiver disponível; build universal (aarch64 + x86_64 + lipo) fica deferido para release prep.

**AC-4:** `apple/project.yml` atualizado para incluir `TorvenCore.xcframework` como dependency do target `Torven`.

**AC-5:** `apple/Torven/ViewModels/CoreBridge.swift` existe com classe `TorvenCoreBridge: ObservableObject` que:
- Chama `getVendorList()` na inicialização
- Expõe `@Published var vendors: [VendorInfo]`

**AC-6:** `apple/Torven/TorvenApp.swift` cria `@StateObject private var coreBridge = TorvenCoreBridge()` e passa via `.environmentObject(coreBridge)`.

**AC-7:** `MenuBarContent.swift` (ou popover inicial) renderiza uma `List` com os 5 vendor names recebidos do Rust — **visível ao rodar o app**.

**AC-8:** Spike AR-3 executado: `leaks` tool rodou por 60 segundos com refresh manual de `getVendorList()` em loop; resultado documentado no Change Log desta story com "zero leaks" ou description de qualquer leak encontrado.

- [x] **T3 — Implementar `apple/scripts/build-xcframework.sh` completo**
  ```bash
  #!/bin/bash
  set -e
  SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"
  REPO_ROOT="$(cd "$SCRIPT_DIR/../.." && pwd)"

  echo "Building torven-core for aarch64..."
  cargo build --release --target aarch64-apple-darwin -p torven-core

  echo "Building torven-core for x86_64..."
  cargo build --release --target x86_64-apple-darwin -p torven-core

  echo "Creating universal binary..."
  mkdir -p "$REPO_ROOT/target/universal/release"
  lipo -create \
    "$REPO_ROOT/target/aarch64-apple-darwin/release/libtorven_core.a" \
    "$REPO_ROOT/target/x86_64-apple-darwin/release/libtorven_core.a" \
    -output "$REPO_ROOT/target/universal/release/libtorven_core.a"

  echo "Creating xcframework..."
  rm -rf "$REPO_ROOT/apple/Frameworks/TorvenCore.xcframework"
  xcodebuild -create-xcframework \
    -library "$REPO_ROOT/target/universal/release/libtorven_core.a" \
    -headers "$REPO_ROOT/crates/torven-core/include/" \
    -output "$REPO_ROOT/apple/Frameworks/TorvenCore.xcframework"

  echo "TorvenCore.xcframework created at apple/Frameworks/"
  ```

    cleanly terminated. `nm` confirms `TorvenCoreBridge.vendors:

- [x] **T11 — Executar spike AR-3: memory profiling com `leaks`** — **RESOLVED ✅**
  - **Spike 1 (Rust-side, tight loop):** Created `crates/torven-core/tests/ar3_leaks_spike.rs`
    which calls `get_vendor_list()` 1,000 times under `leaks --atExit`.
    Command: `leaks --atExit -- ./target/release/deps/ar3_leaks_spike-* --ignored`.
    Result: **`Process 91262: 0 leaks for 0 total leaked bytes`** (869
    nodes malloced for 85 KB, all freed at exit).
  - **Spike 2 (live SwiftUI app, 60s):** Launched `Torven.app` and ran
    `leaks <PID>` after 60 seconds (`getVendorList()` called once at
    `TorvenCoreBridge.init`, kept in `@Published var vendors`).
    Result: **`Process 91582: 0 leaks for 0 total leaked bytes`**
    (28,812 nodes malloced for 4,091 KB; physical footprint 14.3 MB
    peak 14.6 MB).
  - **Conclusion:** UniFFI's reference-counted struct lowering correctly
    frees Rust-owned `Vec<VendorInfo>` allocations on both the immediate
    Swift drop path and the long-lived `@Published` retention path.
    AR-3 is resolved for the `VendorInfo` shape and the general pattern
    of returning Rust-owned `Vec<DictionaryDict>` across the FFI.

### Nota sobre o `TorvenCoreBridge`

O `TorvenCoreBridge` será expandido nas stories futuras para incluir snapshots de uso, insights, etc. O padrão estabelecido aqui é:

```swift
@MainActor
class TorvenCoreBridge: ObservableObject {
    // @Published properties para SwiftUI reactive binding
    // Funções async que delegam para FFI functions (via UniFFI [Async])
    // Erros de FFI convertidos para optionals ou apresentados ao usuário
}
```

A propriedade `static var shared` (singleton) é adicionada em Story 1.15 (necessária para shutdown no AppDelegate). Por enquanto, `@StateObject` no `TorvenApp` é suficiente.

### Cuidados com o xcframework

- `embed: false` no `project.yml` — a staticlib não precisa ser embedded (ela é linked estaticamente)
- O Xcode precisa do header `torven_core.h` para saber o ABI — checar que `crates/torven-core/include/torven_core.h` existe após `make build-core`
- A geração dos Swift bindings (`uniffi-bindgen generate`) NÃO faz parte do `build.rs` — é um step manual que gera arquivos commitados (ou gitignored com regeneração no setup)
- Convenção do projeto: Swift bindings ficam em `apple/Torven/Bridge/Generated/` e headers em `crates/torven-core/include/`; ambos são **gitignored** e regenerados no setup do dev

## Risk: AR-3 — Memory ownership FFI

**Severidade:** HIGH

`Vec<VendorInfo>` cruzando FFI boundary é um caso típico de leak. UniFFI gerencia ownership via reference counting bridge. O spike desta story serve para confirmar que NÃO há leak antes de prosseguir para structs mais complexas.
