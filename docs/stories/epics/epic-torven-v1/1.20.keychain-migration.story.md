# Story 1.20 — Keychain migration: TOML api_keys → macOS Keychain via security-framework

**Story ID:** 1.20.keychain-migration
**Status:** Ready
**Epic:** Torven v1.0 — Pivot macOS native
**Estimated Effort:** M (1 dia, incluindo spike 0.5d obrigatório)

---

## Story (User Story)

Como desenvolvedor do Torven, eu quero implementar o módulo `keychain` em `torven-core` usando o crate `security-framework` com o design de blob JSON por vendor, e fornecer um helper de migration que move `api_key` do TOML para o Keychain na primeira inicialização, para que as API keys dos usuários sejam armazenadas com segurança no macOS Keychain (NFR-3) em vez de em texto plano no `config.toml`.

---

## Contexto e Motivação

NFR-3 do PRD é explícito: "API keys criptografadas em rest via macOS Keychain (não plaintext em config.toml)". Story 1.6 criou o `Account` model com `api_key: Option<String>` — quando `None`, a chave deve ser buscada no Keychain.

Esta story implementa:
1. `MacKeychainStore` via `security-framework` crate
2. `FileFallbackStore` para TUI Linux (sem Keychain)
3. Migration helper: ao encontrar `api_key` no TOML, mover para Keychain e setar `api_key = None`

**Design de blob:** um único item Keychain por vendor com JSON `[{account_id, api_key}]` — evita N prompts de autorização para N accounts (R-6 do PRD).

**Spike obrigatório 0.5d** (citado em ADR-2): validar `security-framework::passwords::set_generic_password` com 5 vendors em macOS real antes de construir o resto.

**Referência:** `docs/architecture/torven-v1-adr.md#adr-2` (Keychain híbrido) e `docs/prd/torven-v1.md#nfr-3`.

## Acceptance Criteria

**AC-1:** Crate `security-framework = "2.10"` adicionada em `crates/torven-core/Cargo.toml` com feature `OSX_10_13` para compatibilidade macOS 13+.

**AC-2:** Trait `SecretStore` definida em `crates/torven-core/src/keychain/mod.rs`:
```rust
pub trait SecretStore: Send + Sync {
    fn get_accounts_blob(&self, vendor: &str) -> Result<Option<Vec<AccountSecret>>, KeychainError>;
    fn set_accounts_blob(&self, vendor: &str, accounts: &[AccountSecret]) -> Result<(), KeychainError>;
    fn delete_vendor_entry(&self, vendor: &str) -> Result<(), KeychainError>;
}

pub struct AccountSecret {
    pub account_id: String,
    pub api_key: String,
}
```

**AC-3:** `MacKeychainStore` implementa `SecretStore` usando `security_framework::passwords::{get_generic_password, set_generic_password, delete_generic_password}`:
- Service name: `com.torven.app.{vendor}` (ex: `com.torven.app.openrouter`)
- Account name: `accounts-blob-v1`
- Password: JSON serializado de `Vec<AccountSecret>`

**AC-4:** `FileFallbackStore` implementa `SecretStore` para TUI Linux:
- Path: `~/.config/torven/secrets/{vendor}.json`
- `chmod 600` após escrita
- Warning log ao usar: `"[WARN] Using file fallback store — não recomendado para produção"`

**AC-5:** Migration helper `fn migrate_keys_to_keychain(config: &mut Config, store: &dyn SecretStore) -> Vec<String>`:
- Para cada vendor em `config.accounts`, se `account.api_key.is_some()`:
  - Adicionar ao blob Keychain do vendor
  - Setar `account.api_key = None` na config
  - Adicionar ao log de warnings retornado
- Salvar config TOML atualizado (api_keys removidos)

**AC-6:** Spike validado: `set_generic_password` + `get_generic_password` funciona para 5 vendors em macOS real. Resultado documentado no Change Log (sucesso ou issue encontrado).

**AC-7:** FFI helpers no UDL:
```udl
namespace torven_core {
    sequence<u8> ffi_keychain_get_blob(string vendor);  // retorna JSON bytes
    void ffi_keychain_set_blob(string vendor, sequence<u8> blob);
};
```

**AC-8:** Testes de integração em `crates/torven-core/tests/keychain_e2e.rs`:
- `test_file_fallback_store_set_get()`: usa `FileFallbackStore` com tempdir
- `test_file_fallback_migration()`: config com api_keys → migration → api_keys None
- Testes macOS real marcados com `#[ignore]` e prefixo `test_mac_keychain_*` (rodam manualmente)

**AC-9:** `cargo test -p torven-core` (sem `--ignored`) passa em CI Linux usando `FileFallbackStore`.

  ```rust
  pub struct MacKeychainStore;

  impl SecretStore for MacKeychainStore {
      fn get_accounts_blob(&self, vendor: &str) -> Result<Option<Vec<AccountSecret>>, KeychainError> {
          let service = format!("com.torven.app.{}", vendor);
          match get_generic_password(&service, "accounts-blob-v1") {
              Ok(bytes) => {
                  let accounts: Vec<AccountSecret> = serde_json::from_slice(&bytes)?;
                  Ok(Some(accounts))
              }
              Err(e) if e.code() == errSecItemNotFound => Ok(None),
              Err(e) => Err(KeychainError::KeychainError(e.to_string())),
          }
      }

      fn set_accounts_blob(&self, vendor: &str, accounts: &[AccountSecret]) -> Result<(), KeychainError> {
          let service = format!("com.torven.app.{}", vendor);
          let blob = serde_json::to_vec(accounts)?;
          set_generic_password(&service, "accounts-blob-v1", &blob)?;
          Ok(())
      }
  }
  ```

## Dev Notes

### Architecture References

- **ADR-2** (`docs/architecture/torven-v1-adr.md#adr-2`): Keychain logic em Rust via `security-framework`. Hot path: vendor fetchers Rust precisam da api_key para cada request HTTP. Mantém secret store no mesmo crate elimina coreografia Swift → FFI → Rust.
- **ADR-2 Layout**: `crates/torven-core/src/keychain/mac.rs` com `MacKeychainStore`, `fallback.rs` com `FileFallbackStore`.
- **R-6** (`docs/prd/torven-v1.md#9-risks`): Single Keychain item por vendor com payload JSON de N accounts — evita N prompts de autorização.
- **NFR-3** (`docs/prd/torven-v1.md#nfr-3`): "API keys criptografadas em rest via macOS Keychain (não plaintext em config.toml)". Logs redatam keys (mesma disciplina de `src/anthropic/creds.rs`).

### security-framework Crate

`security_framework::passwords::set_generic_password(service, account, password: &[u8])`:
- `service`: identifica o app (`com.torven.app.{vendor}`)
- `account`: identifica o tipo de dado (`accounts-blob-v1`)
- `password`: bytes arbitrários (JSON serializado)

O Keychain item fica em `login.keychain-db` do usuário. O app precisa de `com.apple.security.keychain-access-groups` no entitlement — mas para desenvolvimento sem assinatura, funciona sem (os prompts de autorização aparecem).

### Schema do Blob Keychain

```json
{
  "version": 1,
  "accounts": [
    { "account_id": "openrouter-clienteacme", "api_key": "sk-or-..." },
    { "account_id": "openrouter-personal", "api_key": "sk-or-xxx" }
  ]
}
```

Versionado com `version` field para migration futura do schema do blob.
