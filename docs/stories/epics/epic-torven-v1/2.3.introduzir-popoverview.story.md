# Story 2.3 — Introduzir PopoverView.swift — popover real (header + container vazio)

**Story ID:** 2.3.introduzir-popoverview
**Status:** InReview
**Epic:** Torven v1.0 — Pivot macOS native (`epic-torven-v1`)
**Wave:** 2 — SwiftUI Skeleton
**Estimated Effort:** S (0.5 dia — 2 arquivos criados/modificados, sem nova lógica de negócio)

---

## Story (User Story)

Como desenvolvedor do Torven preparando a Wave 3 (vendor cards), eu quero substituir o stub `VendorListView` no happy path por um `PopoverView.swift` real com estrutura de header + container vazio, para que o Wave 3 encontre o path `apple/Torven/Popover/PopoverView.swift` criado, com dimensões documentadas (360×420 como ponto de partida para UX-Q1), e com `MenuBarContent.swift` já apontando para ele em vez do stub histórico — eliminando o último elo que ligava `TorvenApp` ao artefato preservado da Story 1.5.

---

## Contexto e Motivação

A Story 2.1 formalizou a estrutura de pastas do ADR §4 e criou `MenuBarContent.swift` como camada de indireção — com `MenuBarContent` delegando temporariamente para `VendorListView()` (stub da Story 1.5). A Story 2.2 adicionou `MenuBarLabel.swift` com SF Symbol configurável. Esta story, 2.3, fecha o ciclo da Wave 2: substitui a delegação temporária por uma `PopoverView` real.

**O que esta story entrega:**
- `apple/Torven/Popover/PopoverView.swift` — struct SwiftUI com header "Torven" + Spacer + container vazio (`.frame(width: 360, height: 420)`)
- `MenuBarContent.swift` refatorado para usar `PopoverView()` em vez de `VendorListView()`
- `VendorListView_Story15.swift` ainda compilável como artefato de preservação, mas **fora do happy path**

**Por que o popover ficará visualmente vazio:** A Wave 3 ainda não chegou — os vendor cards entram nas Stories 3.x. Isso é INTENCIONAL. A regressão visual (popover sem cards) é documentada explicitamente no Dev Notes e é reversível em 1 commit caso Wave 3 atrase.

**Referência:** `docs/architecture/torven-v1-adr.md#4` (NEW Apple side — estrutura de files), `docs/architecture/torven-v1-adr.md § Story Roadmap entry 10` ("Popover skeleton — main popover view"), `docs/architecture/torven-v1-adr.md#8` (UX-Q1 — sizing trade-offs 360×420 vs 380×540).

## Dev Notes

### Regressão Visual Esperada (INTENCIONAL)

Após esta story, o usuário que clicar no status item do Torven verá um **popover vazio** com apenas o título "Torven". Os 5 vendor cards visíveis após a Story 1.5 **não aparecem mais**. Isso é comportamento correto e esperado:

- A Story 2.3 desacopla o happy path do stub de preservação
- Os vendor cards voltam na Wave 3 (Stories 3.x), implementados corretamente sobre a estrutura `PopoverView`
- Esta regressão é **reversível em 1 commit** caso Wave 3 atrase (basta fazer `MenuBarContent` apontar de volta para `VendorListView_Story15`)

O @dev deve documentar isso explicitamente no Change Log e no Dev Agent Record. O @qa não deve marcar como FAIL por "popover vazio" — esse é o estado esperado de DoD desta story.

### Frame Size 360×420 — Ponto de Partida, Não NFR Final

O ADR §8 (UX-Q1) documenta o trade-off entre 360×420 e 380×540:
- 360×420 é o tamanho citado no PRD (`docs/prd/torven-v1.md`)
- 380×540 acomoda 5 vendor cards completos sem scroll (5×90px + header 50px = 500px > 420px)
- UX-Q1 permanece **aberta** e será fechada pelo @ux-design-expert na Wave 3

**Decisão Story 2.3:** adotar 360×420 como ponto de partida documentado. O `.frame(width: 360, height: 420)` NÃO deve ser tratado como NFR imutável. Se Wave 3 exigir 380×540, o change é 1 linha em `PopoverView.swift`.

[AUTO-DECISION] Frame size para Story 2.3 → 360×420 (ponto de partida PRD) em vez de 380×540 (sizing completo Wave 3). Razão: UX-Q1 ainda aberta; Wave 2 não precisa da decisão final; 360×420 é o valor PRD correto para placeholder sem vendor cards. O comment no arquivo documenta explicitamente que revisão ocorre em Wave 3.

### Architecture References

- **ADR §4 (`docs/architecture/torven-v1-adr.md`):** tabela "NEW (Apple side)" confirma `apple/Torven/Popover/PopoverView.swift` como "Main popover view (header + 5 vendor cards)". Esta story entrega o arquivo sem os 5 cards (Wave 3).
- **ADR §11 — Story Roadmap entry 10:** "SwiftUI Popover skeleton — `PopoverView` com header (Insights/Refresh/Settings buttons) + 5 VendorCard placeholders". Esta story entrega apenas o header — os botões e cards são Wave 3+.

### Por que NÃO introduzir botões (Insights/Refresh/Settings) agora

O ADR §11 entry 10 menciona "header (Insights/Refresh/Settings buttons)" para a popover skeleton. Esses botões são escopo Wave 3+ (conectam a lógica de AI Insights, settings, e refresh tick). Introduzi-los sem a lógica seria mais stub que estrutura. A decisão de scope de Lorenzo (2026-06-04) confirma: Wave 2 entrega header + container vazio.

### Technical Constraints

- macOS deployment target: **13.0** (herdado de Story 1.1, preservado em `project.yml`)
- `LSUIElement: true` continua no Info.plist (app menu bar, sem dock icon)
- `embed: false` no TorvenCore.xcframework continua (staticlib, herdado de Story 1.5)
- `@EnvironmentObject coreBridge: TorvenCoreBridge` permanece no `TorvenApp.swift` scope — `PopoverView` nesta story NÃO precisa acessar o coreBridge (container vazio, sem vendor data). Se o Dev injetar `.environmentObject(coreBridge)` no `MenuBarExtra` body (via `MenuBarContent`), está OK — mas `PopoverView` não precisa declarar `@EnvironmentObject` ainda.

### Testing Requirements

Esta story não introduz lógica nova testável por XCTest. Os gates de qualidade são:
- Build verde via `xcodebuild -scheme Torven -configuration Debug build`
- Smoke run manual (T5): ícone + popover header + popover vazio
- Workspace Rust verde (`cargo test/clippy/fmt`)

Compatível com ADR §10 (Testing strategy — XCTest target completo entra na Story 1.21+ release prep, não Wave 2).
