# Story 3.2 — PopoverView ForEach 5 vendors + UX-Q1 closure (frame 360×420 vs 380×540)

**Story ID:** 3.2.popover-foreach-vendors
**Status:** Done
**Epic:** Torven v1.0 — Pivot macOS native (`epic-torven-v1`)
**Wave:** 3 — Vendor Cards + Account Picker
**Estimated Effort:** S (~0.5 dia — 1 arquivo modificado, sem nova lógica, decisão empírica UX-Q1)

---

## Story (User Story)

Como desenvolvedor do Torven fechando o popover principal da Wave 3, eu quero substituir o `if-let` defensivo da Story 3.1 (que renderiza só OpenRouter) por um `ForEach(coreBridge.vendors, id: \.id) { VendorCard(vendor:) }` que renderiza os 5 vendors em sequência (Anthropic → OpenAI → OpenRouter → Z.AI → Gemini conforme ordem canônica `get_vendor_list()`), e fechar definitivamente a UX-Q1 do ADR §8 — decidir empiricamente se `frame(width: 360, height: 420)` (PRD starting point) acomoda os 5 cards sem scroll OU se precisa subir para `380×540` — para que a Wave 3 deixe o popover funcionalmente completo antes da Story 3.3 introduzir o AccountPicker.

---

## Contexto e Motivação

A Story 3.1 entregou `VendorCard.swift` como skeleton parametrizado e plugou **um** card (OpenRouter) no `PopoverView` como prova de integração. Esta story 3.2 escala isso para os 5 vendors via `ForEach` e mede empiricamente se o frame escolhido na Wave 2 (360×420 como PRD starting point, documentado como "sujeito a revisão em UX-Q1, Wave 3" no header comment de `PopoverView.swift`) ainda funciona — ou se a empilhamento de 5 cards força o salto para 380×540.

**UX-Q1 — o que é:** o ADR `docs/architecture/torven-v1-adr.md` §8 lista 6 perguntas abertas para o @ux-design-expert (UX-Q1 a UX-Q6). UX-Q1 é a única que pode ser fechada sem `@ux` envolvido — é uma decisão dimensional empírica:

> "UX-Q1: Popover sizing — 360×420 (PRD starting point) vs 380×540 (acomoda 5 vendor cards completos sem scroll, header 50px + 5×90px ≈ 500px > 420px). Trade-off: menor footprint visual vs scroll-free render."

Decisão Lorenzo (kickoff Wave 3, handoff `wave3-kickoff-master-to-sm`): "UX-Q1 closure dentro de 3.2 — decisão empírica: implementar com 360×420 e ajustar p/ 380×540 se 5 cards full não couberem sem scroll. Sem micro-story 3.0."

**O que esta story entrega:**
- `PopoverView.swift` refatorado: `if-let` → `ForEach(coreBridge.vendors, id: \.id)` renderizando 5 `VendorCard(vendor:)`
- Spacing/padding entre cards definido empiricamente (8-12pt vertical entre cards)
- UX-Q1 fechada: `frame(width:, height:)` finalizada em **360×420** (preferred) OU **380×540** (se cards forem cortados/scrollados)
- Benchmark NFR-1: popover open warm <50ms (PRD §6.5) verificado em smoke run
- ADR §8 UX-Q1 marcada como CLOSED com a decisão documentada inline ou em changelog do ADR

**Referências:**
- `docs/architecture/torven-v1-adr.md#8` — UX-Q1 a UX-Q6
- `docs/architecture/torven-v1-adr.md` §11 Story Roadmap entry 12 — "Extend cards to all 5 vendors"

**AC-1:** `apple/Torven/Popover/PopoverView.swift` refatorado de `if-let openRouter` (Story 3.1) para `ForEach`:
```swift

        .padding(.horizontal, 16)
}
```
- Identificador estável `id: \.id` (slug do Rust, garantido único — ver `torven_core.udl` linha 53-55 e `VendorListView_Story15.swift` linha 24 que usa o mesmo padrão)

- Header "Torven" preservado acima do ForEach
- `Spacer()` REMOVIDO se houver — o ForEach preenche o espaço

**AC-2:** UX-Q1 closure — `frame(...)` em `PopoverView` reflete decisão empírica:
- **Caso A (preferred):** `.frame(width: 360, height: 420)` mantido se 5 cards full couberem sem scroll. Header comment do arquivo atualizado: "UX-Q1 CLOSED 2026-06-04: 360×420 ratificado — 5 cards full visíveis."
- **Caso B (fallback):** `.frame(width: 380, height: 540)` adotado se cards forem visualmente comprimidos ou requererem scroll. Header comment: "UX-Q1 CLOSED 2026-06-04: 380×540 adotado — 360×420 forçava scroll/clipping."
- Em AMBOS os casos: ADR §8 UX-Q1 line marked CLOSED com decisão + razão (1 linha no ADR ou changelog appendix).

**AC-3:** Body resultante de `PopoverView` (caso A, preferred):
```swift
var body: some View {
    VStack(spacing: 0) {
        Text("Torven")
            .font(.title3)
            .fontWeight(.semibold)
            .frame(maxWidth: .infinity, alignment: .leading)
            .padding(.horizontal, 16)
            .padding(.vertical, 12)

        VStack(spacing: 8) {
            ForEach(coreBridge.vendors, id: \.id) { vendor in
                VendorCard(vendor: vendor)
            }
        }
        .padding(.horizontal, 16)

        Spacer(minLength: 0)
    }
    .frame(width: 360, height: 420)
}
```
Variações de spacing (8/10/12pt) e alignment OK contanto que os 5 cards apareçam todos sem scroll (caso A) ou scroll-free no frame escolhido (caso B).

## Dev Notes

### Por que UX-Q1 closure aqui é seguro sem @ux-design-expert

Lorenzo decidiu no kickoff Wave 3 (handoff `wave3-kickoff-master-to-sm`):

O critério de decisão é **dimensional**, não estilístico — "os 5 cards full cabem sem scroll?" tem resposta binária empírica. @ux não precisa opinar nisso.

Se algo **estilístico** emergir durante o smoke (ex: contraste do background do card, sparkline color, font weight), @dev anota para Wave 4 — esta story NÃO redesenha o card (AC-9 reforça).

### Por que `id: \.id` e não outro identificador

`VendorInfo.id` é slug lowercase do Rust (`"anthropic"`, `"openai"`, etc.) garantido único pela função `get_vendor_list()` (validado no spike Story 1.5 e documentado no UDL linha 53-55). `VendorListView_Story15.swift` linha 24 já usa esse mesmo padrão — manter consistência.

Não usar `id: \.displayName` (não garantido único contra futuros vendors com nomes similares) nem `id: \.self` (Swift exige `Hashable` em VendorInfo — não implementado e fora de escopo).

### NFR-1 benchmark: limites e expectativa

PRD §6.5 lista NFR-1 como "popover open <50ms warm". Esta story renderiza 5 VendorCard estáticos sem async/disk/network — overhead é puramente render time da árvore de views. Expectativa razoável:
- **p50 esperado:** 5-15ms (cards são VStack/HStack simples sem state mutation)
- **p99 esperado:** <30ms
- **Alerta:** se p99 >50ms warm consistentemente, há algo no env de dev (mac antigo? Xcode debug overhead?) — não bloqueia esta story, mas vira nota para Wave 4

`CFAbsoluteTimeGetCurrent()` é precisão de ns no mac — suficiente. Se quiser ser mais formal, `os_signpost` + Instruments é o padrão Apple, mas overkill para esta story.

### Por que NÃO adicionar GroupBox/Section em volta do ForEach

Tentação natural: empilhar visualmente os 5 cards num `Section` ou `GroupBox`. Razão para NÃO fazer aqui:
1. Cada `VendorCard` já tem seu próprio `RoundedRectangle` background (Story 3.1 AC-3) — section em volta cria visual ruído duplo
2. Wave 4 introduz Settings UI que pode querer reaproveitar a list de vendors num formato diferente — manter o ForEach no `PopoverView` simples permite que `VendorCard` seja reutilizado sem precisar desempacotar de `Section`
3. ADR §11 entry 12 fala só de "Extend cards to all 5 vendors" — não menciona grupamento visual

Se um agrupamento visual for necessário depois (separar configured vs unconfigured), isso vira escopo de Wave 4 — não desta.

### Ordem canônica dos vendors

`torven_core.udl` linhas 248-252 documentam: "Order is significant: the menu-bar app renders vendors in the order returned here. Current order matches the rollout / market-share priority used in the legacy Waybar widget (Anthropic first, OpenAI second, then OpenRouter, Z.AI, Gemini)."

O `ForEach` consome essa ordem direto sem sort/filter. Se Lorenzo quiser mudar a ordem (ex: alfabética), é mudança no Rust `get_vendor_list()`, não no Swift.
