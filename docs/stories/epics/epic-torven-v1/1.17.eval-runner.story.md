# Story 1.17 — Eval runner bin (torven-evals) + dataset 30 casos rotulados

**Story ID:** 1.17.eval-runner
**Status:** Ready
**Epic:** Torven v1.0 — Pivot macOS native
**Estimated Effort:** L (1.5-2 dias)

---

## Story (User Story)

Como desenvolvedor do Torven, eu quero o binário `torven-evals` em `crates/torven-core` com dataset de 30 casos rotulados em `evals/dataset.jsonl`, métricas de faithfulness, relevance, latência e custo, e um Markdown report gerado por `cargo run --bin torven-evals`, para que o pipeline de eval público do AI Insights seja estabelecido e a regressão seja detectável em CI.

---

## Contexto e Motivação

O eval pipeline é o **moat defensável** do Torven contra competidores que "vibe-code" AI features (PRD §9, R-4). Sem evals públicos, o AI Insights é marketing; com evals, é engenharia.

Esta story entrega o eval runner funcional com dataset mínimo de 30 casos. Não exige chamadas reais à API Anthropic — usa `MockLlmClient` da Story 1.15 por padrão, com opção `--real-llm` para rodar com API key real.

**Pode rodar em paralelo com Story 1.15** após a interface `LlmClient` estar definida (a Story 1.17 consome a trait, não precisa da implementação real).

**Referência:** `docs/prd/torven-v1.md#6.1-eval-pipeline` e `docs/architecture/torven-v1-adr.md#adr-8` (Eval runner Rust nativo).

## Acceptance Criteria

**AC-1:** `crates/torven-core/evals/dataset.jsonl` com exatamente 30 casos. Cada linha é JSON com campos:
```json
{
  "id": "eval-001",
  "usage_snapshot": { ... },  // anonimizado, agregado
  "expected_category": "anomaly | trend | budget_risk | optimization_opportunity",
  "expected_severity": "info | warning | critical",
  "partial_ideal_response": "string (trecho do insight esperado)"
}
```

**AC-2:** Schema do dataset documentado em `crates/torven-core/evals/schema.md`.

**AC-3:** `crates/torven-core/src/bin/torven-evals.rs` existe (não mais stub) e ao rodar `cargo run --bin torven-evals -- --dataset evals/dataset.jsonl` produz relatório Markdown com:
- Número de casos: total, passou, falhou
- **Faithfulness score:** % de claims no output com evidência no input
- **Relevance score:** % de outputs categorizados como "actionable"
- **Latency p50/p95** (sintético — baseado em timing do MockLlmClient)
- **Cost p50/p95** (calculado via token counter, sem chamada real)
- Baseline target publicado: faithfulness ≥0.85, relevance ≥0.80

**AC-4:** `crates/torven-core/src/insights/eval.rs` contém:
- `fn compute_faithfulness(output: &InsightsOutput, context: &InsightsContext) -> f64`: heurística de verificação de evidências
- `fn compute_relevance(output: &InsightsOutput) -> f64`: verifica se output contém verbo de ação e número concreto

**AC-5:** Report pode ser salvo em arquivo: `cargo run --bin torven-evals -- --dataset evals/dataset.jsonl --output evals/results/report-{date}.md`

**AC-6:** `--real-llm` flag opcional que usa `RealAnthropicClient` (requer `ANTHROPIC_API_KEY` env var). Sem a flag, usa `MockLlmClient` com respostas pré-definidas do dataset.

**AC-7:** `cargo run --bin torven-evals` sem argumentos mostra usage claro com `--help`.

**AC-8:** `evals/results/` está em `.gitignore` (resultados são artefatos, não fonte).

**AC-9:** `cargo test -p torven-core -- eval` roda os testes de eval como testes Rust opcionais (sem `--ignore` — mas marcados com `#[test]` normal para rodar com `cargo test`).

## Dev Notes

### Architecture References

- **ADR-8** (`docs/architecture/torven-v1-adr.md#adr-8`): Eval runner Rust nativo. `[[bin]] name="torven-evals"`. Trait `LlmClient` com `RealAnthropicClient` + `MockLlmClient`. Dataset JSONL. Markdown report.
- **ADR-8 bônus inesperado**: sem Tauri, o eval runner é puro Rust — roda em CI Linux sem cross-compilation ou webkit2gtk.
- **PRD §6.1** (`docs/prd/torven-v1.md#6.1-eval-pipeline`): Dataset mínimo 30 casos. Métricas: faithfulness ≥0.85, relevance ≥0.80. Regressão >5% bloqueia merge.
- **PRD §6.2** (`docs/prd/torven-v1.md#6.2-prompt-versioning`): `prompts/insights.v{N}.md` git-tracked. `eval_baseline_score` no frontmatter preenchido após o primeiro run desta story.

### Nota sobre MockLlmClient no Eval

O `MockLlmClient` para evals é **diferente** do mock para testes unitários. No eval:
- Para cada caso do dataset, o mock retorna uma resposta **gerada deterministicamente** baseada no `usage_snapshot` — não uma resposta hardcoded
- Isso permite que a heurística de faithfulness funcione (o mock "gera" claims que estão no contexto)
- O eval com `--real-llm` é o groundtruth — o mock é para CI rápido sem custo

Implementação sugerida: `MockLlmClient::for_eval()` recebe o contexto e gera uma `InsightsOutput` que inclui números do contexto de forma previsível.
