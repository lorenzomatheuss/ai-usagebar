# Story 5.3 — Refresh button na Main Window + status feedback end-to-end

**Story ID:** 5.3.refresh-button-main-window
**Status:** Done
**Epic:** Torven v1.0 — Pivot macOS native (`epic-torven-v1`)
**Wave:** 5 — Settings + Real API
**Estimated Effort:** S (~0.5 dia — SwiftUI button + async Task + feedback states + chart reload; Rust FFI já pronto em 5.1)

---

## Story (User Story)

Como usuário do Torven que configurou suas API keys em Settings, eu quero clicar em "Refresh" na Main Window — ou pressionar Cmd+R — para que o app faça requisições reais às APIs dos vendors configurados, grave os novos snapshots, e atualize o chart automaticamente, para que eu possa ver meu gasto real de hoje sem abrir o terminal.

---

## Contexto e Motivação

Esta story fecha o loop end-to-end do milestone "testar com APIs reais":

```
Story 5.2 (Settings) → API key salva no Keychain
Story 5.1 (ffi_refresh_vendor) → fetcher Rust executa, grava snapshot
Story 5.3 (Refresh button) → dispara 5.1, recarrega chart via ffi_query_aggregated
```

O `ChartViewModel` já tem o padrão de `reload()` que chama `ffi_query_aggregated` e `getBudgetStatus()` (Story 4.3 + 4.6). Esta story adiciona um método `refresh(vendors:)` que chama `ffi_refresh_vendor` para cada vendor configurado e, ao concluir, chama `reload()`.

**Decisão WAVE5-D3 (cravada):** Refresh = manual-only em Wave 5. Sem timer/scheduler. O botão "Refresh" no top bar da Main Window é a única entrada de trigger.

**Decisão WAVE5-D5 (cravada):** Sem AI Insights nesta story — deferred Wave 5.5/6.

**Vendors configurados = vendors com Keychain blob:** A função `ffi_keychain_get_blob(vendor)` retorna `CredentialMissing` se não há key. A lógica de "quais vendors refreshar" em Swift: tentar `ffi_keychain_get_blob` para cada vendor e incluir somente os que retornam `Ok` — ou chamar `ffi_refresh_vendor` para todos os 4 e deixar o Rust retornar `CredentialMissing` silenciosamente para os não configurados (opção mais simples, preferida — @dev decide e documenta).

**Referências ADR:**
- ADR-4 — UniFFI `[Async]`; `ffiRefreshVendor` é `async throws` em Swift — deve ser chamado dentro de `Task { }`
- Story 4.3 `ChartViewModel.reload()` — padrão a seguir para manter consistência
- Story 4.6 — `getBudgetStatus()` chamado no `reload()` — deve continuar após refresh

## Acceptance Criteria

**AC-1:** Botão "Refresh" visível no top bar da `MainWindowView.swift`:
- Label: `Image(systemName: "arrow.clockwise")` com `Text("Refresh")` (ou label-only — @dev decide com olho no espaço disponível no top bar Wave 4)
- Atalho de teclado: `.keyboardShortcut("r", modifiers: .command)` (Cmd+R)
- Localização: top bar, à direita do `ChartMetricPicker` (ou onde couber sem comprimir os pickers Wave 4 — decisão @dev, documentar no Change Log)

**AC-2:** Ao clicar "Refresh", o botão entra em estado de loading:
- Botão desabilitado (`.disabled(isRefreshing)`)
- Ícone rotativo ou `ProgressView` inline substituindo o ícone de seta enquanto `isRefreshing == true`
- `@Published var isRefreshing: Bool = false` em `ChartViewModel`

**AC-3:** `ChartViewModel` ganha método `refresh()` (ou `refreshAll()`):
```swift
func refresh() async {
    isRefreshing = true
    defer { isRefreshing = false }
    
    let vendors = ["anthropic", "openai", "openrouter", "zai"]
    for vendor in vendors {
        do {
            try await TorvenCore.ffiRefreshVendor(vendorName: vendor)
        } catch RefreshFfiError.credentialMissing {
            // silencioso — vendor não configurado
        } catch {
            // logar erro sem interromper os outros vendors
            refreshErrors[vendor] = error.localizedDescription
        }
    }
    reload() // recarregar chart com dados novos
}
```

**AC-4:** Após `refresh()` completar, `ChartViewModel.reload()` é chamado automaticamente — o chart e o BudgetBurn gauge atualizam com os novos dados (via `ffi_query_aggregated` + `getBudgetStatus()`).

**AC-5:** Feedback de erro não-bloqueante:
- Se um ou mais vendors falham com erro que não é `CredentialMissing` (ex: `NetworkError`, `ApiError`), exibir uma `Text` de status abaixo do top bar ou como banner — estilo análogo ao `errorMessage` já existente em `MainWindowView.swift` (Wave 4)
- Formato: `"Refresh parcial: openrouter falhou (sem rede)"` — lista dos vendors que falharam
- Banner desaparece após 5s ou ao próximo Refresh bem-sucedido
- `CredentialMissing` NÃO aparece como erro (esperado para vendors não configurados)

**AC-6:** Se NENHUM vendor tem credencial configurada (todos retornam `CredentialMissing`), exibir mensagem orientativa:
- `"Nenhum vendor configurado. Abra Settings (Cmd+,) para adicionar suas API keys."`
- Como `Text` temporária no mesmo slot de feedback (AC-5), desaparece após 8s

**AC-7:** O botão Refresh na Main Window é acessível via `accessibilityLabel("Atualizar dados de uso")` e `.accessibilityHint("Busca dados reais das APIs configuradas")`.

**AC-8:** `xcodebuild` BUILD SUCCEEDED com o botão integrado em `MainWindowView.swift` + `ChartViewModel.swift` atualizado.

**AC-9 (edge case — Cmd+R conflict):** Se outro componente da Main Window já capturar Cmd+R (improvável mas verificar), @dev usa `.onKeyDown` ou outro shortcut disponível. Documentar no Change Log.

## Risks

| Risco | Severidade | Mitigação |
|---|---|---|
| `ChartViewModel.reload()` é síncrono mas `ffi_query_aggregated` pode ser blocking: verificar se `reload()` já executa em background `Task`. Se não, adicionar `Task { @MainActor in ... }` wrapper no `refresh()`. | Low | Inspecionar `ChartViewModel.reload()` antes de T1; se síncrono, wrappear em `Task { await MainActor.run { reload() } }` ou similar. |
| Top bar Wave 4 com 3 pickers + botão Refresh pode ficar dense em janela estreita (~900pt). | Low | WAVE5-D3 crava o botão no top bar mas @dev tem flexibilidade de layout (texto abreviado, icon-only, toolbar item). Documentar no Change Log. |
| `ffiRefreshVendor` é `async throws` mas o erro Swift é do tipo `RefreshFfiError` — exige `catch let e as RefreshFfiError` explícito (não `catch`). | Low | T1 trata explicitamente cada case de `RefreshFfiError` no `do/catch` de `refresh()`. |
| `isRefreshing` bloqueia novos refreshes durante execução: se a operação de fetch de um vendor travar (timeout 10s por vendor = até 40s total para 4 vendors em sequência), o UI fica no estado loading. | Medium | Os fetchers têm `HTTP_TIMEOUT: Duration::from_secs(10)` em Rust. 4 × 10s = 40s worst-case. Para Wave 5 é aceitável (manual refresh, usuário pode esperar). Wave 5.5 pode adicionar `Task.timeout` ou execução paralela dos vendors. |
