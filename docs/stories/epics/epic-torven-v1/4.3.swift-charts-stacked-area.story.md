# Story 4.3 — Swift Charts foundation + Stacked area cost chart

**Story ID:** 4.3.swift-charts-stacked-area
**Status:** InReview
**Epic:** Torven v1.0 — Pivot macOS native (`epic-torven-v1`)
**Wave:** 4 — Main Window + Swift Charts
**Estimated Effort:** M (~1 dia — aggregation layer Rust→Swift + AreaMark stacked + ChartViewModel + legend + perf)

---

## Story (User Story)

Como usuário do Torven na janela de histórico, eu quero ver um gráfico de área empilhada mostrando o custo em USD por vendor ao longo do tempo, para que eu consiga visualizar de forma imediata quanto estou gastando em cada vendor e como os custos evoluíram no período selecionado.

---

## Contexto e Motivação

Esta story entrega o **chart principal** da Main Window e, mais importante, a **foundation de charts**: `ChartViewModel` + `AggregatedSample` que todas as stories seguintes (4.4, 4.5, 4.6) vão reutilizar ou estender. É o investimento de infraestrutura que desbloqueia as 3 stories de chart restantes da Wave 4.

**Decisão WAVE4-D4 (cravada):** Todos os 4 chart types são entregues nesta wave. Esta story entrega o chart 1/4 (stacked area cost) e a fundação para os demais.

Depende de Story 4.0.5 (FFI ffi_query_aggregated) para consumir TimeBucket[] aggregated data. Sem 4.0.5, esta story está bloqueada.

**Arquitetura do pipeline de dados:**
```
SQLite GROUP BY (Rust) ──FFI──► ChartViewModel.swift ──► AggregatedSample[] ──► Chart { AreaMark }
    ↑                              ↑
ffi_query_aggregated()        observa MainWindowViewModel.$dateRange via Combine
(Story 4.0.5)
```

**Estratégia de buckets (delegada ao Rust):**
A estratégia de bucket é controlada pelo enum `BucketStrategy` (UDL, da Story 4.0.5):
- `.auto` (default em Wave 4) → range ≤ 7d → Hourly; ≤ 30d → Daily; > 30d → Weekly (limits AC-4 da 4.0.5)
- Hard cap garantido pela 4.0.5: ~840 buckets × 5 vendors = 4200 AreaMark no pior caso (7d hourly)

**Performance NFR:**
ADR §6 nota: "Performance teto se v1.5 trouxer históricos longos (~10k+ pontos). Mitigação: downsample server-side Rust." Para Wave 4, target: render < 100ms para 30d × 5 vendors (30 buckets × 5 = 150 marks). Worst-case 7d × 5 vendors = 840 marks aceitável.

**Referências ADR:**
- `docs/architecture/torven-v1-adr.md` ADR-6 — Swift Charts, API declarativa, `AreaMark`, `.stacked`, legend
- `docs/architecture/torven-v1-adr.md` ADR-5 — SQLite + history layer
- Story 4.0.5 — `ffi_query_aggregated`, `TimeBucket`, `BucketStrategy` UDL surface (BLOCKER)
- `docs/architecture/torven-v1-adr.md` ADR-4 — async FFI + `Task { }` pattern

### Design decisions & deviations

**D-1 (ChartViewModel composition — init-time dependency):** The clean pattern for "view model A depends on view model B at init" in macOS 13 (no `@Observable`) is a private sub-view (`ChartContent`) that takes the parent VM as `@ObservedObject` and creates the child VM via `StateObject(wrappedValue:)` in its `init`. Top-level `MainWindowView` can't do this directly because its own `@StateObject viewModel` isn't published into `self` at init time. This keeps both VMs as `@StateObject`s (single source of truth per view identity) without resorting to a singleton or environment object for the chart VM.

**D-2 (Combine over `.onChange`):** Story risk #3 flagged that `.onChange` has different signatures on macOS 13 vs 14+. `mainViewModel.$dateRange.sink` (with `.removeDuplicates()`) gives the same behavior on both targets, and the in-process Combine publisher delivers the *current* value to new subscribers automatically — so no separate "first load" kick is needed.

**D-3 (Lazy `ffi_init_history`):** Wave 4 has not added an app-startup hook for `ffi_init_history`. ChartViewModel calls it lazily on first `reload(for:)` and caches an `historyInitialized` flag. The Rust impl is idempotent (`*slot = Some(db)` overwrites), so re-running on failure is safe. If init fails, an error message is published and the chart degrades to the empty-state view (AC-4) + the inline red banner explains why.

**D-4 (Task cancellation):** Range changes that arrive while a prior `ffiQueryAggregated` is still in flight cancel the previous task. Each task body checks `Task.isCancelled` before publishing, so stale results never overwrite fresh ones — important because the FFI call is synchronous from Swift's POV (no await inside it) but the surrounding `Task` block allows cooperative cancellation between init + query.

**D-5 (Hover annotation snap-to-sample):** AC-6's `chartProxy.value(atX:)` returns the *interpolated* date at the cursor's x, which would float the dashed RuleMark between bucket boundaries. Snapping to the closest sample timestamp (`min(by: timeIntervalSince)`) makes the guide line and the annotation card always line up with real data points — a small UX improvement that costs nothing.

**D-6 (`.chartPlotStyle { $0.compositingGroup() }` NOT applied):** T6 inspection in the 840-marks preview rendered smoothly on the Apple Silicon dev box. Per AC-8, the modifier is a one-line add if Wave 5 polish reveals jank on the smallest supported hardware. Documented here to make the trade-off explicit instead of pre-optimizing.

**D-7 (Vendor color palette):** Brand-aligned 5-color palette (purple/orange/dark-green/blue + gray-reserved for Gemini). `KeyValuePairs` (not `[String: Color]`) so Swift Charts gets a deterministic iteration order for the legend.

**Deviation from AC-9:** No XCTest target exists in `apple/project.yml` for Story 4.3 (the xcodegen project has `testTargets: []` and no `Tests/` folder anywhere in `apple/`). Adding an XCTest scheme + target is a non-trivial scope expansion (project regeneration + plist + scheme files) that's better done as its own story (Wave 4 polish or Story 4.7+ test infrastructure). The `fromFFI` logic is straightforward enough that the `#Preview "7 days × 5 vendors (mock)"` exercises the function with 840 input buckets at preview-time and is visible verification; story 4.0.5 AC-7/8/9/10 already covers the Rust aggregation. Logging this as Outstanding for QA awareness.
