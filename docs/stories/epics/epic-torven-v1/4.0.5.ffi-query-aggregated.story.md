# Story 4.0.5 — FFI ffi_query_aggregated — temporal-bucket aggregation no torven-core

**Story ID:** 4.0.5.ffi-query-aggregated
**Status:** Done
**Epic:** Torven v1.0 — Pivot macOS native (`epic-torven-v1`)
**Wave:** 4 — Main Window + Swift Charts
**Estimated Effort:** S (~0.5 dia — UDL declaration + Rust GROUP BY impl + 4 testes)
**Owner:** @data-engineer (Dara)

---

## Story (User Story)

Como desenvolvedor implementando os Swift Charts da Wave 4, eu quero uma função FFI `ffi_query_aggregated` que execute a agregação temporal diretamente em SQLite (GROUP BY bucket), para que os gráficos de área e grids de vendors possam consumir `TimeBucket[]` pré-calculados sem realizar client-side aggregation em Swift (o que seria ~100× mais lento e violaria o NFR-1 de performance).

---

## Contexto e Motivação

A UDL atual expõe `ffi_query_snapshots` (raw events paginados). As Stories 4.3, 4.4 e 4.5 precisam de **dados temporalmente agregados por bucket** (hora/dia/semana) para alimentar `AreaMark` e `LineMark` nos Swift Charts. Sem esta story, cada story de chart teria que:

1. Chamar `ffi_query_snapshots` em loop paginado (~43K events em 30d)
2. Agregar por bucket em Swift — proibido pelo NFR-1 ADR §6 (performance teto)

**Decisão WAVE4-D7 (cravada pelo Lorenzo):** Path A — adicionar `ffi_query_aggregated` ao namespace `torven_core{}`. SQLite `GROUP BY bucket_start` é ~100× mais rápido que client-side e a mesma API será reutilizada por Wave 6 evals.

**Pipeline de dados esperado após esta story:**
```
SQLite (Rust GROUP BY)
  ──ffi_query_aggregated()──►  TimeBucket[]  ──►  ChartViewModel (Story 4.3)
```

**Estratégia de bucket_size_ms (BucketStrategy::Auto):**
- range ≤ 7 dias → Hourly (3_600_000 ms) — máximo 168 buckets
- range ≤ 30 dias → Daily (86_400_000 ms) — máximo 30 buckets
- range > 30 dias → Weekly (604_800_000 ms) — máximo ~52 buckets/ano

Estes limites garantem que o número de marks nos charts nunca ultrapasse ~840 × 5 vendors = 4200 AreaMark no pior caso (7d hourly × 5 vendors), que é o teto documentado em Story 4.3 AC-8.

**Referências ADR:**
- `docs/architecture/torven-v1-adr.md` ADR-4 — UniFFI UDL mode, type conventions
- `docs/architecture/torven-v1-adr.md` ADR-6 — Swift Charts, performance NFR-1
- Story 1.13 — `history/db.rs` (padrão de query com `rusqlite`, `HistoryDb.connection()`)
- `crates/torven-core/src/torven_core.udl` — `ffi_query_snapshots` como irmão de referência
- `crates/torven-core/src/uniffi_exports.rs` — padrão `ffi_*` + `HistoryFfiError` mapping

## Acceptance Criteria

**AC-1 — UDL: `dictionary TimeBucket` declarado exatamente como:**
```udl
dictionary TimeBucket {
    i64 bucket_start_ts;    // Unix ms, inclusive
    i64 bucket_end_ts;       // Unix ms, exclusive
    string vendor;
    string? account_id;      // null quando account_filter_mode = AggregateAcrossAccounts
    f64 cost_sum_usd;
    u64 tokens_sum;
    u32 request_count;
    string metric_kind;
};
```
Em `crates/torven-core/src/torven_core.udl`, na seção de dictionaries (após `PagedHistorySnapshots`).

**AC-2 — UDL: `enum BucketStrategy` declarado exatamente como:**
```udl
enum BucketStrategy {
    "Auto",
    "Hourly",
    "Daily",
    "Weekly"
};
```
Em `crates/torven-core/src/torven_core.udl`, na seção de enums (após `HistoryAccountFilterMode`).

**AC-3 — UDL: função `ffi_query_aggregated` declarada no `namespace torven_core {}` exatamente como:**
```udl
[Throws=HistoryFfiError]
sequence<TimeBucket> ffi_query_aggregated(
    string vendor,
    HistoryAccountFilterMode account_filter_mode,
    string? account_id,
    i64 since_ts,
    i64 until_ts,
    BucketStrategy bucket_strategy
);
```
`vendor = ""` (string vazia) significa "todos os vendors". `account_id` é ignorado quando `account_filter_mode != Specific`.

**AC-4 — Rust: `history::query_aggregated` executa SQLite GROUP BY conforme estratégia:**

A query SQL interna usa exatamente:
```sql
SELECT
  (ts / bucket_size_ms) * bucket_size_ms AS bucket_start,
  vendor,
  (CASE WHEN ? = 'AggregateAcrossAccounts' THEN NULL ELSE account_id END) AS account_id,
  SUM(COALESCE(cost_usd, 0.0)) AS cost_sum,
  SUM(COALESCE(tokens_used, 0)) AS tokens_sum,
  COUNT(*) AS request_count,
  metric_kind
FROM history
WHERE ts >= ? AND ts < ?
  AND (? = '' OR vendor = ?)
GROUP BY bucket_start, vendor, account_id, metric_kind
ORDER BY bucket_start ASC;
```

`bucket_size_ms` derivado de `BucketStrategy`:
- `Hourly` → 3_600_000
- `Daily` → 86_400_000
- `Weekly` → 604_800_000
- `Auto` → pick conforme `until_ts - since_ts`:
  - ≤ 7 dias (604_800_000 ms) → Hourly
  - ≤ 30 dias (2_592_000_000 ms) → Daily
  - > 30 dias → Weekly

**AC-5 — Return contract:**
- Buckets sem dados são **omitidos** (não retorna zero-rows; Swift faz fill-gaps na UI se quiser)
- Ordem: ASC por `bucket_start_ts`
- Range sem dados → `Ok(vec![])`, não erro
- `account_id` em cada `TimeBucket` é `Some` quando `account_filter_mode = Specific`; `None` quando `AggregateAcrossAccounts` ou `All`
- `metric_kind` preservado da coluna `metric_kind` da tabela `history` (sem normalização — vendors expõem `cost_usd_total`, `tokens_used`, `pct_used` heterogeneamente)

**AC-6 — Rust impl em `uniffi_exports.rs`: `pub fn ffi_query_aggregated(...)` segue o padrão de `ffi_query_snapshots`:**
- Acessa `HISTORY_DB` via `OnceLock` (mesmo padrão de inicialização lazy do `ffi_query_snapshots`)
- Mapeia `HistoryError` → `HistoryFfiError` (mesmo mapping existente)
- Chama `db.query_aggregated(...)` no `HistoryDb`

**AC-7 — Teste Rust: 3 eventos no mesmo bucket horário → 1 `TimeBucket` com somas corretas:**

Dado: 3 `UsageSnapshot` com:
- `vendor = "anthropic"`, `ts` dentro do mesmo bloco horário (ex: `3600000..7199999` ms)
- `cost_usd = Some(0.01)`, `Some(0.02)`, `Some(0.03)`
- `tokens_used = Some(100)`, `Some(200)`, `Some(300)`

Quando: `query_aggregated("anthropic", All, None, since=0, until=10_000_000, BucketStrategy::Hourly)`

Então: retorna `vec![TimeBucket { cost_sum_usd: 0.06, tokens_sum: 600, request_count: 3, ... }]` (1 bucket).

**AC-8 — Teste Rust: 2 eventos em buckets diferentes → 2 `TimeBucket` ordenados ASC:**

Dado: 2 snapshots com `ts` em blocos horários distintos (ex: `ts=3600001` e `ts=7200001`)

Quando: `query_aggregated` com `BucketStrategy::Hourly`

Então: retorna 2 `TimeBucket` com `bucket_start_ts` em ordem crescente; `bucket_start_ts[1] > bucket_start_ts[0]`.

**AC-9 — Teste Rust: `BucketStrategy::Auto` seleciona granularidade corretamente:**
- Range 7d (since=0, until=604_800_000): usa Hourly (verifica via `bucket_end_ts - bucket_start_ts == 3_600_000`)
- Range 30d (since=0, until=2_592_000_000): usa Daily (verifica via `bucket_end_ts - bucket_start_ts == 86_400_000`)
- Range 60d (since=0, until=5_184_000_000): usa Weekly (verifica via `bucket_end_ts - bucket_start_ts == 604_800_000`)

**AC-10 — Teste Rust: filtro de vendor e account filter mode:**
- `vendor = ""` (string vazia): retorna buckets de todos os vendors no range
- `vendor = "openrouter"`: retorna apenas buckets do vendor "openrouter"
- `account_filter_mode = AggregateAcrossAccounts`: `TimeBucket.account_id = None` em todos os buckets
- `account_filter_mode = Specific` com `account_id = Some("openrouter-acme")`: filtra pela conta

**AC-11 (opcional) — Bench informal documentado no Change Log:**
- `query_aggregated` com 10K eventos em 30d diário (`bucket_size = Daily`) → execução < 50 ms
- Medido em `cargo test -- --nocapture` ou benchmark manual
- Resultado documentado no Change Log como baseline para NFR-1 Wave 4 charts

## Risks

| Risco | Severidade | Mitigação |
|---|---|---|
| `metric_kind` heterogeneity — eventos podem ter `cost_usd_total` OU `tokens_used` OU `pct_used`; GROUP BY precisa incluir `metric_kind` para não misturar tipos diferentes num mesmo bucket | High | SQL já inclui `metric_kind` no GROUP BY e no SELECT — buckets são separados por metric_kind, não agregados entre kinds. Documentado no return contract AC-5. |
| Bucket boundary alignment — `(ts / bucket_size_ms) * bucket_size_ms` usa divisão inteira de i64; para timestamps Unix ms isso funciona mas presume UTC implicitamente | Medium | Wave 4 usa UTC consistentemente (mesmo padrão de `ffi_query_snapshots`). Timezone issue adiado para Wave 5 se necessário. Documentar no Change Log. |
| `u64 tokens_sum` vs `i64 tokens_used` — a coluna `tokens_used` na tabela `history` é `i64?`; `SUM` pode retornar `NULL` ou negativo se dados corrompidos | Low | `COALESCE(tokens_used, 0)` na query garante que NULL → 0. Cast para `u64` no mapeamento Rust: `as u64` com saturação (valores negativos impossíveis em produção). |
| Compilação UDL após adições — UniFFI falha o build se UDL e Rust driftem | Low | T5 gate explícito: `cargo build -p torven-core` antes de marcar T1-T3 completos. |

### Deviations from spec (documented for QA)

1. **Implementation location:** T2 specified `pub fn query_aggregated(&self, ...)` method on `impl HistoryDb` in `db.rs`. Implemented as free function `pub fn query_aggregated(db: &HistoryDb, ...)` in `history/mod.rs` to match the established codebase pattern (`query_snapshots_paged`, `record_snapshot`, `run_retention_janitor` are all free functions in `mod.rs`). The call site in `uniffi_exports.rs` becomes `history::query_aggregated(db, ...)` instead of `db.query_aggregated(...)`. Semantically identical.

2. **SQL: table name.** AC-4 SQL `FROM history` was a spec error — the actual table is `usage_snapshots` (see `migrations/001_initial.sql`). Used the real table name.

3. **SQL: branched per `AccountFilter` instead of single CASE-WHEN query.** AC-4 SQL used a single sentinel-string CASE WHEN to project `account_id` as NULL for `AggregateAcrossAccounts`, but kept `GROUP BY ... account_id ...` on the raw column. Under `All` mode this would emit one row per real `account_id` value — all with `account_id = NULL` projected — which violates the AC-10 contract ("AggregateAcrossAccounts merges accounts into a single bucket"). Branched per `AccountFilter::{All, Null, Specific}` with SQL specific to each mode (mirrors the established pattern in `query_snapshots_paged`). The AC-10 test `ac_10_aggregate_across_accounts_emits_none_account_id` validates the corrected semantic (two accounts → 1 merged bucket, not 2 bucket-rows).
