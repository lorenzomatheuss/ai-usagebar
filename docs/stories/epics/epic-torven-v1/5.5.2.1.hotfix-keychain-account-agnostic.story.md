## Story (User Story)

Como usuário do Torven logado no Claude Code app, eu quero que o badge Anthropic em Settings mostre 🟢 Conectado e o botão Refresh do Anthropic funcione — para que o app reflita corretamente meu OAuth e busque usage real sem precisar do legacy `~/.claude/.credentials.json`.

---

## Root Cause (diagnóstico 2026-06-07)

A Story 5.5.2 (Wave 5.5) introduziu probe Keychain via:

```rust
security_framework::passwords::get_generic_password(service, "")
//                                                            ^^ empty account
```

baseado no spike `docs/architecture/spikes/claude-code-keychain-schema.md` que documentou "account is empty — `security` CLI shows no account qualifier". O spike confundiu dois comportamentos:

| Lookup | Resultado |
|---|---|
| `security find-generic-password -s "Claude Code-credentials" -a "lorenzorodrigues"` | ✅ acha |
| `security find-generic-password -s "Claude Code-credentials" -a ""` | ❌ `errSecItemNotFound` |
| `security find-generic-password -s "Claude Code-credentials"` (sem `-a`) | ✅ acha (CLI default = wildcard) |

O CLI sem `-a` é **leniente** (matches qualquer account). O Rust `security-framework::passwords::get_generic_password(svc, "")` é **strict** — exige account exato. Confirmado em dev box Lorenzo (acct=`lorenzorodrigues`, mdat=2026-06-07): probe retorna `errSecItemNotFound` silencioso, fallback file também não existe → badge "Não configurado".

**Não é regressão da 5.5.2 deploy** — a impl sempre teve o bug; o spike é que estava errado. O CI passou porque os testes 5.5.2 usavam `service` randômico (negative path) ou file-based (`read_from`).

---

## Fix Strategy — Opção B (account-agnostic search)

Substituir `passwords::get_generic_password(svc, "")` por `ItemSearchOptions` filtrando apenas por `kSecAttrService` — espelha exatamente o comportamento do `security` CLI sem `-a`. Tolera qualquer account que o Claude Code use agora ou no futuro.

Para write_back, descobrir o blob existente via mesma query account-agnostic, mas re-escrever via `set_generic_password(service, $USER, bytes)` — Claude Code usa `$USER` como convention, então isso *atualiza* a entry existente em vez de criar duplicada com account vazio.

**Por que B em vez de A (hardcoded `$USER`):**
- Read fica resiliente se Claude Code mudar convention no futuro
- Write usa `$USER` apenas porque precisa de UM account específico para escrever (Keychain API exige); se Claude Code mudar, write criará uma duplicada mas read continuará achando ambas — degradação suave, não falha silenciosa
- Tradeoff documentado no comment do `write_back_to_keychain`

O spike `docs/architecture/spikes/claude-code-keychain-schema.md` precisa ser atualizado para corrigir a assertion sobre account. Adicionar nota no topo:

```markdown
**CORREÇÃO 2026-06-07 (Story 5.5.2.1):** A documentação original afirmava
"account is empty" baseado em `security` CLI sem `-a`. Isso é parcialmente
verdade — o CLI sem `-a` é leniente e match qualquer account. Mas a entry
real do Claude Code é qualificada com `kSecAttrAccount = $USER`. Probe via
Rust `security-framework` deve usar `ItemSearchOptions` account-agnostic
(filtrar apenas `kSecAttrService`) — NÃO `get_generic_password(svc, "")`,
que é strict e falha contra entries com account não-vazio.
```
