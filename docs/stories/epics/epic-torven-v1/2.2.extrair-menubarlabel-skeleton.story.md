# Story 2.2 — Extrair MenuBarLabel.swift — SF Symbol configurável (skeleton)

**Story ID:** 2.2.extrair-menubarlabel-skeleton
**Status:** InReview
**Epic:** Torven v1.0 — Pivot macOS native (`epic-torven-v1`)
**Wave:** 2 — SwiftUI Skeleton
**Estimated Effort:** S (0.5 dia — refactor puro, sem código novo de negócio)

---

## Story (User Story)

Como desenvolvedor do Torven preparando a Wave 2 (SwiftUI Skeleton), eu quero extrair a definição do SF Symbol da barra de status para uma struct `MenuBarLabel: View` configurável em `apple/Torven/MenuBar/MenuBarLabel.swift`, para que o ícone do menu bar deixe de ser hardcoded em `TorvenApp.swift` e a Wave 7 consiga trocar o symbol por uma label dinâmica (baseada em vendor pressure, AR-8 spike) sem refactor cascata no entry point do app.

---

## Contexto e Motivação

Após Story 2.1 (formalizar estrutura + introduzir `MenuBarContent`), o `TorvenApp.swift` ainda usa:

```swift
MenuBarExtra("Torven", systemImage: "chart.bar.fill") {
    MenuBarContent()
        .environmentObject(coreBridge)
}
```

O `systemImage: "chart.bar.fill"` está hardcoded diretamente no parâmetro `label` do `MenuBarExtra`. Isso não é um problema funcional, mas é um acoplamento de configuração: quando a Wave 7 precisar usar um SF Symbol diferente ou introduzir um label dinâmico (lendo vendor pressure do Rust core via FFI, AR-8), vai ter que mexer no `TorvenApp.swift` — o entry point `@main` do app.

Esta story isola essa decisão em `MenuBarLabel.swift`, criando uma struct mínima que:
1. Recebe o SF Symbol como parâmetro configurável (com um `.default` conveniente que preserva `chart.bar.fill`)
2. Renderiza o `Image(systemName:)` correspondente
3. É usada por `TorvenApp` como label customizado do `MenuBarExtra`

**Por que agora?** O ADR §4 já lista `apple/Torven/MenuBar/MenuBarLabel.swift` como path esperado, e o ADR §11 (entry 8) descreve esta story como "MenuBarLabel skeleton — SF Symbol configurável; placeholder para label dinâmico de Wave 7". A pasta `apple/Torven/MenuBar/` foi criada pela Story 2.1 — o momento natural é agora.

**Por que NÃO introduzir label dinâmico agora?** A Wave 7 (AR-8 spike) requer dados do Rust core via FFI async e edge cases de multi-monitor. Entregar isso aqui quebraria o princípio de story atomicidade e violaria a decisão de Lorenzo de 2026-06-04 de adiar AR-8. Esta story entrega **apenas** a configurabilidade estática do symbol.

**Referências:**
- `docs/architecture/torven-v1-adr.md §4` — path `apple/Torven/MenuBar/MenuBarLabel.swift` com função "NSStatusItem custom view content (dynamic label)"
- `docs/architecture/torven-v1-adr.md §7` AR-8 — NSStatusItem multi-monitor (explicitamente fora do escopo desta story)
- `docs/architecture/torven-v1-adr.md §11` entry 8 — "NSStatusBar tray + dynamic label" roadmap entry
- Story 2.1 (Done) — cria `apple/Torven/MenuBar/` e introduz `MenuBarContent`

## Acceptance Criteria

**AC-1:** `apple/Torven/MenuBar/MenuBarLabel.swift` criado com struct `MenuBarLabel: View` que:
- Aceita um parâmetro `symbol: String` (SF Symbol name)
- Renderiza `Image(systemName: symbol)` no body
- Expõe uma constante estática `.default` (ou `static let defaultSymbol = "chart.bar.fill"`) para não forçar o call site a hardcodar o string
- É um `View` struct puro — sem `@State`, sem `@EnvironmentObject`, sem nenhuma dependency do Rust core

Exemplo de implementação mínima aceitável:

```swift
import SwiftUI

struct MenuBarLabel: View {
    static let defaultSymbol = "chart.bar.fill"

    let symbol: String

    var body: some View {
        Image(systemName: symbol)
    }
}
```

**AC-2:** `apple/Torven/TorvenApp.swift` atualizado para usar `MenuBarLabel` como label customizado do `MenuBarExtra`, substituindo o parâmetro `systemImage: "chart.bar.fill"` pela forma de label-view:

```swift
MenuBarExtra {
    MenuBarContent()
        .environmentObject(coreBridge)
} label: {
    MenuBarLabel(symbol: MenuBarLabel.defaultSymbol)
}
.menuBarExtraStyle(.window)
```

O header comment do `TorvenApp.swift` atualizado para mencionar que Story 2.2 extraiu o symbol para `MenuBarLabel`.

**AC-3:** Paridade funcional visual preservada: o ícone exibido na status bar continua sendo `chart.bar.fill`, visualmente idêntico ao da Wave 1 / Story 2.1. Nenhuma alteração perceptível ao usuário.

**AC-4:** `apple/Torven/MenuBar/.gitkeep` (introduzido pela Story 2.1 como placeholder) removido, pois `MenuBarLabel.swift` passa a ser o arquivo real da pasta.

**AC-5:** Build verde:
```bash
make build-core && cd apple && xcodegen generate && \
  DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  xcodebuild -scheme Torven -configuration Debug build
```
deve completar com **BUILD SUCCEEDED**.

**AC-6:** Smoke run preserva paridade funcional Wave 1/2.1:
- `Torven.app` abre sem crash
- Ícone `chart.bar.fill` visível na status bar do macOS
- Click no ícone abre o popover (via `MenuBarContent → VendorListView`, conforme estado pós-2.1)
- Sem erros novos em Console.app filtrados por process `Torven`

**AC-7:** Workspace Rust intacto:
```bash
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --check
```
Esta story é pure Swift refactor. Os três comandos devem passar sem mudança no Rust.

## Dev Notes

### Architecture References

- **ADR §4 (`docs/architecture/torven-v1-adr.md`, linha ~1036):** tabela NEW Apple side lista `apple/Torven/MenuBar/MenuBarLabel.swift` com função "NSStatusItem custom view content (dynamic label)". Esta story cria exatamente esse arquivo — mas como skeleton estático (o "dynamic label" da Wave 7 é trabalho futuro).
- **ADR §7 AR-8 (`docs/architecture/torven-v1-adr.md`, linha ~1458):** NSStatusItem multi-monitor positioning bugs. Explicitamente **fora do escopo** desta story. O design de `MenuBarLabel` (symbol como parâmetro) **deixa a porta aberta** para Wave 7 passar um symbol dinâmico sem refactor em `TorvenApp.swift`.
- **ADR §11 entry 8 (`docs/architecture/torven-v1-adr.md`, linha ~1348):** "NSStatusBar tray + dynamic label — MenuBarExtra label dinâmico (lê de Rust core via FFI). MenuBarContent placeholder. Spike de 0.5d para edge cases multi-monitor (AR-8)." — Esta story entrega o skeleton/placeholder; o "lê de Rust core" é Wave 7.

### Por que `MenuBarLabel(symbol:)` e não `MenuBarLabel(systemImage:)`?

[AUTO-DECISION] Nomear o parâmetro `symbol:` vs `systemImage:` → `symbol:` (razão: é o nome usado pela própria Apple internamente para SF Symbol names em contextos programáticos; evita confusão com o parâmetro `systemImage:` do `MenuBarExtra` que estamos substituindo — mantém semântica diferente clara no call site)

### Por que usar a forma de label-view trailing closure do MenuBarExtra?

A API `MenuBarExtra { content } label: { label }` permite passar qualquer `View` como label, enquanto a forma `MenuBarExtra("Torven", systemImage:)` aceita apenas um `String` de system image diretamente. Ao migrar para a forma de label-view:
- `TorvenApp` delega inteiramente a aparência do label para `MenuBarLabel`
- Wave 7 pode enriquecer `MenuBarLabel` (adicionar Text, cor, etc.) sem tocar o `MenuBarExtra` call
